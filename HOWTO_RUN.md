# Как запустить MyMoney (после Этапа 4)

Этот документ — практическое руководство: что установить, как поднять
бэкенд (§ 1–2, macOS / Linux / Windows), как собрать и запустить приложение
на Android-смартфоне (§ 3–4) и на iOS — симулятор или реальный iPhone
(§ 4A, нужен Mac с Xcode).

> **Нужен только бэкенд?** Установите Docker и JDK 17 (§ 1), затем из корня
> проекта: `./scripts/run-backend.sh` (macOS / Linux) или
> `.\scripts\run-backend.ps1` (Windows). Подробности — § 2.

> **Что уже работает.**
> - Этапы 1–3 — офлайновая работа приложения (счета, категории, операции,
>   бюджеты, цели, аналитика, PDF).
> - **Этап 4** — семейные приглашения, облачная синхронизация push/pull.
>   Для этого нужен запущенный бэкенд.
> - Приложение по-прежнему работает без сети (Offline First): всё, что нужно
>   для базового ведения бюджета, доступно и без входа в учётную запись.

---

## 1. Что установить

Бэкенду нужны только **Docker** и **JDK 17+**. Flutter и Android Studio нужны
для мобильного приложения (§ 3–4), для запуска сервера они не требуются.

| Инструмент | Версия | Для чего |
|---|---|---|
| **Docker** | последняя | Локальный PostgreSQL для бэкенда |
| **JDK 17+** (Temurin/Homebrew) | ровно 17 или новее | Компиляция и запуск Ktor-сервера |
| **Flutter SDK** | 3.24+ | Только для мобильного приложения |
| **Android Studio** | последняя | Только для Android: SDK, эмулятор, adb |
| **Xcode** | последняя | Только для iOS (нужен Mac) |

### macOS

```bash
brew install --cask docker      # затем один раз запустить Docker.app
brew install openjdk@17
brew install --cask flutter     # только если собираете мобильное приложение
```

Homebrew не кладёт `java` в PATH автоматически. Проверьте и при
необходимости добавьте в `~/.zshrc`:

```bash
sudo ln -sfn /opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk \
             /Library/Java/JavaVirtualMachines/openjdk-17.jdk
export JAVA_HOME="$(/usr/libexec/java_home -v 17)"
```

### Linux (Debian/Ubuntu)

```bash
sudo apt install openjdk-17-jdk docker.io docker-compose-plugin
sudo usermod -aG docker "$USER"     # чтобы docker работал без sudo; нужен релогин
```

### Windows

```powershell
winget install Docker.DockerDesktop
winget install EclipseAdoptium.Temurin.17.JDK
```

### Проверка

```bash
docker --version
docker info          # должен отработать без ошибок — значит демон запущен
java -version        # должно быть 17 или новее
```

`java -version` показывает 1.8 или 11 при установленном 17? Значит в PATH
чужая Java. На macOS: `export JAVA_HOME="$(/usr/libexec/java_home -v 17)"`.

## 2. Запуск бэкенда

Есть два пути: скрипт (одна команда, сам проверит окружение) и руками
(понятно, что именно происходит). Начните со скрипта; ручной путь — § 2.3.

### 2.1. Быстрый путь: скрипт

```bash
# macOS / Linux — из корня проекта
./scripts/run-backend.sh
```

```powershell
# Windows
.\scripts\run-backend.ps1
```

Скрипт делает всё сам: читает `.env` (создаёт с dev-дефолтами, если его нет),
проверяет JDK 17+ и запущенный Docker, поднимает Postgres, ждёт, пока
контейнер станет `healthy`, экспортирует переменные окружения и стартует
сервер. Первый запуск качает Gradle и зависимости — 3–5 минут; дальше секунды.

Готово, когда в логе появится:

```
Application started in 1.276 seconds.
Responding at http://0.0.0.0:8080
```

**Команды скрипта** (одинаковые в обеих версиях):

| Команда | Что делает |
|---|---|
| `start` *(по умолчанию)* | Postgres + сервер через Gradle. Ctrl+C останавливает сервер, Postgres продолжает работать |
| `jar` | Собрать fat jar и запустить его — ближе к тому, что уезжает в production |
| `db` | Только Postgres; сервер запускаете из IDE |
| `stop` | Остановить сервер и контейнер |
| `restart` | `stop` + `start` |
| `status` | Состояние Postgres, сервера и ответ `/healthz` |
| `test` | Тесты бэкенда (Testcontainers, нужен Docker) |
| `logs` | Хвост лога фонового сервера |
| `psql` | `psql` внутри контейнера |

**Опции:** `-p 9090` (другой порт), `-d` / `-Detach` (в фон, лог в
`backend/build/backend.log`), `--no-db` / `-NoDb` (не трогать Docker),
`--clean` / `-Clean`, `--offline` / `-Offline`, `--help`.

```bash
./scripts/run-backend.sh start -d     # в фоне — терминал остаётся свободным
./scripts/run-backend.sh status       # что сейчас работает
./scripts/run-backend.sh logs         # смотреть лог
./scripts/run-backend.sh stop         # выключить всё
```

Если PowerShell отказывается запускать скрипт («выполнение сценариев
отключено»):

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
# или разово:
powershell -ExecutionPolicy Bypass -File .\scripts\run-backend.ps1
```

### 2.2. Ловушка: локальный Postgres перехватывает порт

Самая коварная проблема на машине разработчика, и скрипт её специально ловит.

Если у вас установлен **нативный** PostgreSQL (Homebrew, `apt`, установщик
EDB), он слушает конкретно `127.0.0.1:5432` и `[::1]:5432`. Контейнер же
публикует порт на wildcard `*:5432`. Более специфичная привязка выигрывает,
поэтому `localhost:5432` уходит **в нативный Postgres**, а контейнер остаётся
недостижимым.

Коварство в том, что `docker compose ps` показывает контейнер `healthy`
(`pg_isready` не проверяет учётку), а бэкенд падает с сообщением, которое
уводит в другую сторону:

```
HikariPool$PoolInitializationException: Failed to initialize pool:
FATAL: role "mymoney" does not exist
```

Роль есть — просто вы стучитесь не в ту базу. Два выхода:

```bash
# 1) Развести по портам — ничего не ломает (в .env):
#    POSTGRES_PORT=5434
#    DB_URL=jdbc:postgresql://localhost:5434/mymoney
docker compose up -d --force-recreate postgres

# 2) Погасить локальный Postgres:
brew services stop postgresql@18    # macOS
sudo systemctl stop postgresql      # Linux
```

Проверить, кто на самом деле слушает порт:

```bash
lsof -nP -iTCP:5432 -sTCP:LISTEN    # macOS / Linux
```

Строка с `postgres` и адресом `127.0.0.1` — это нативный сервер;
`com.docke` или `docker-proxy` — контейнер.

> На **этой машине** уже применён вариант 1: в `.env` стоит
> `POSTGRES_PORT=5434`, потому что 5432 занят Homebrew `postgresql@18`,
> а 5433 — контейнером другого проекта.

### 2.3. Ручной путь: те же шаги без скрипта

Полезно, если скрипт падает или нужно понять, что именно происходит.

**Шаг 1 — переменные окружения.** `.env` не в git (в нём секреты). Если его
нет, создайте — рабочий набор dev-значений есть в § 2.4. Он читается и
`docker-compose`, и — после экспорта — сервером.

**Шаг 2 — поднять Postgres.** Из корня проекта:

```bash
docker compose up -d postgres
docker compose ps                    # ждём STATUS = healthy
```

Поднимется `localhost:${POSTGRES_PORT}`, база `mymoney`, пользователь
`mymoney`, пароль `mymoney_dev_password`. Данные лежат в volume
`mymoney-postgres-data` и переживают перезапуск контейнера.

**Шаг 3 — экспортировать переменные и запустить сервер.** Ktor читает
`application.conf`, где каждое значение переопределяется переменной
окружения (`${?DB_URL}` и т.д.). Без экспорта возьмутся дефолты из конфига —
а там порт 5432, что на этой машине неверно.

```bash
# macOS / Linux
set -a; . ./.env; set +a
cd backend
chmod +x ./gradlew      # на свежем клоне бит +x часто теряется
./gradlew run
```

```powershell
# Windows
Get-Content .env | Where-Object { $_ -match '^\s*[^#].*=' } | ForEach-Object {
    $k, $v = $_ -split '=', 2
    [Environment]::SetEnvironmentVariable($k.Trim(), $v, 'Process')
}
cd backend
.\gradlew.bat run
```

Миграции применять отдельно не нужно: Flyway прогоняет
`V1__initial_schema.sql` … `V3__email_verification.sql` при старте
приложения и заодно засевает системные категории.

**Альтернатива — fat jar** (стартует быстрее, не держит Gradle-демон):

```bash
cd backend && ./gradlew buildFatJar
java -jar build/libs/mymoney-backend.jar
```

**Альтернатива — всё в Docker** (бэкенд тоже в контейнере, нужен `JWT_SECRET`):

```bash
JWT_SECRET="$(openssl rand -base64 48)" docker compose --profile prod up -d
```

**Остановка.** `Ctrl+C` в окне Gradle + `docker compose stop postgres`.

> ⚠️ `Ctrl+C` не всегда убивает сервер. `./gradlew run` запускает приложение
> потомком **Gradle-демона**, а не своим, поэтому JVM с сервером может
> пережить остановку Gradle и продолжить держать порт 8080. Проверка и
> зачистка:
>
> ```bash
> lsof -nP -iTCP:8080 -sTCP:LISTEN
> kill <PID>
> ```
>
> `scripts/run-backend.sh stop` делает это автоматически — и убивает только
> процесс, в командной строке которого есть `mymoney.ApplicationKt` или
> `mymoney-backend.jar`, чтобы не задеть чужое приложение на том же порту.

### 2.4. Что лежит в `.env`

```bash
# === Postgres (читается docker-compose и бэкендом) ===
POSTGRES_DB=mymoney
POSTGRES_USER=mymoney
POSTGRES_PASSWORD=mymoney_dev_password
POSTGRES_PORT=5434          # 5432, если нет конфликта с локальным Postgres

# === Backend ===
APP_ENV=development
PORT=8080
BACKEND_PORT=8080
DB_URL=jdbc:postgresql://localhost:5434/mymoney   # порт обязан совпадать с POSTGRES_PORT
DB_USER=mymoney
DB_PASSWORD=mymoney_dev_password
DB_POOL_SIZE=10

# === JWT ===
JWT_SECRET=dev-only-change-me-in-production
JWT_ISSUER=mymoney
JWT_AUDIENCE=mymoney-mobile
JWT_ACCESS_TTL_MINUTES=15
JWT_REFRESH_TTL_DAYS=30

# === Почта ===
# Пусто — коды пишутся в лог. Заполните, чтобы включить SMTP.
MAIL_HOST=
MAIL_PORT=587
MAIL_USERNAME=
MAIL_PASSWORD=
MAIL_FROM=no-reply@mymoney.local
MAIL_STARTTLS=true
MAIL_SSL=false
```

### Почта: коды подтверждения

Регистрация требует кода из письма. Есть два режима, переключает `MAIL_HOST`:

| `MAIL_HOST` | Что происходит |
|---|---|
| пусто *(по умолчанию)* | `LoggingVerificationCodeSender` — код пишется в лог, письма нет. Для dev достаточно |
| задан | `SmtpVerificationCodeSender` — реальная отправка по SMTP |

В `APP_ENV=production` почта **обязательна**: без `MAIL_HOST` сервер откажется
стартовать. Иначе код подтверждения уходил бы только в лог, и ни один
пользователь не смог бы завершить регистрацию.

```bash
MAIL_HOST=smtp.yandex.ru
MAIL_PORT=587
MAIL_USERNAME=no-reply@example.com
MAIL_PASSWORD=<пароль приложения>
MAIL_FROM=no-reply@example.com
MAIL_STARTTLS=true      # порт 587
MAIL_SSL=false          # для implicit TLS на 465: STARTTLS=false, SSL=true
```

Письмо уходит в двух частях (`text/plain` + `text/html`), STARTTLS
обязателен (`starttls.required`), таймауты — 10 секунд.

Два подводных камня:

- **`POSTGRES_PORT` и порт в `DB_URL` должны совпадать.** Меняете один —
  меняйте оба. Скрипт предупредит о расхождении, `docker compose` — нет.
- **`APP_ENV=production` включает fail-safe** (`AppConfig.kt`): сервер
  откажется стартовать, если `JWT_SECRET` остался дефолтным или короче
  32 символов, либо если `DB_PASSWORD` дефолтный. Для прода:
  `openssl rand -base64 48`.

`POSTGRES_USER` / `POSTGRES_PASSWORD` применяются **только при первой
инициализации** пустого volume. Поменяли их у уже созданной базы — контейнер
запустится со старой учёткой, а бэкенд упадёт на `role does not exist`.
Пересоздать (**удалит все данные в базе**):

```bash
docker compose down && docker volume rm mymoney-postgres-data
```

### 2.5. Проверить, что бэкенд отвечает

```bash
# Health-check
curl -s http://localhost:8080/healthz
# {"status":"ok","db":"up"}
```

`"db":"down"` — сервер жив, но не видит базу: смотрите § 2.2.

Полный поток регистрации (macOS / Linux):

```bash
# Шаг 1. Регистрация — токенов НЕ выдаёт, только высылает 6-значный код
curl -s -X POST http://localhost:8080/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"me@example.com","password":"password123"}'
# 202 Accepted: {"email":..., "codeExpiresAt":..., "resendAvailableAt":...}

# Шаг 2. Код взять из лога бэкенда. В development почта не отправляется —
# LoggingVerificationCodeSender пишет строку вида:
#   [DEV] Email confirmation code for me@example.com is 123456 (valid until ...)
# Если сервер запущен в фоне скриптом:
grep "code for me@example.com" backend/build/backend.log | tail -1
# Настроить реальную отправку — заменить биндинг VerificationCodeSender
# в mymoney/di/AppModule.kt на SMTP-реализацию.

# Шаг 3. Подтверждение — вот здесь выдаются токены
curl -s -X POST http://localhost:8080/v1/auth/verify-email \
  -H "Content-Type: application/json" \
  -d '{"email":"me@example.com","code":"123456"}'
# Вернёт accessToken, refreshToken, userId, familyId

# Код потерялся? Повторная отправка (не чаще раза в минуту):
curl -s -X POST http://localhost:8080/v1/auth/resend-code \
  -H "Content-Type: application/json" \
  -d '{"email":"me@example.com"}'

# Список системных категорий (accessToken из шага 3)
TOKEN="<вставь accessToken>"
curl -s http://localhost:8080/v1/categories -H "Authorization: Bearer $TOKEN"
```

То же на Windows — через `curl.exe`, с экранированием кавычек в теле:

```powershell
curl.exe -X POST http://localhost:8080/v1/auth/register `
  -H "Content-Type: application/json" `
  -d '{\"email\":\"me@example.com\",\"password\":\"password123\"}'
```

Успешный ответ `/v1/categories` со списком системных категорий означает, что
работает вся цепочка: Postgres → Flyway → Koin → JWT → авторизованный роут.

### 2.6. Прогнать автотесты бэкенда

Docker должен быть запущен — Testcontainers поднимет **отдельный** Postgres
на случайном порту, ваш dev-контейнер не трогает.

```bash
./scripts/run-backend.sh test
# или руками:
cd backend && ./gradlew test
```

Юнит + интеграция для auth, accounts, categories, transactions — ~30–60 секунд.

## 3. Сборка мобильного приложения

### 3.1. Установить зависимости и сгенерировать код

```powershell
cd mobile
flutter pub get
```

Есть три варианта:

**A. Windows-приложение на самом ПК** (быстрая проверка UI без телефона):

```powershell
flutter run -d windows
```

**B. Android-эмулятор** (Android Studio → Device Manager → Play):
Затем в PowerShell:
```powershell
flutter devices                     # проверить, что эмулятор виден

```

**C. Реальный Android-смартфон** — см. § 4 ниже.

**D. iOS-симулятор или реальный iPhone** (нужен Mac) — см. § 4A ниже.

## 4. Запуск и тест на реальном Android-смартфоне

### 4.1. Подготовить телефон

1. **Включить режим разработчика:**
   Настройки → О телефоне → нажать «Номер сборки» 7 раз.
2. **Включить USB-debugging:**
   Настройки → Для разработчиков → Отладка по USB.
3. **Подключить телефон USB-кабелем** к ПК.
4. **На телефоне** — разрешить отладку с этого ПК (появится диалог при
   первом подключении, поставить галочку «Всегда»).

### 4.2. Проверить, что ПК видит телефон

```powershell
flutter devices
```

В списке должна появиться модель вашего телефона. Если её нет:
- переустановить драйверы через Android Studio → SDK Manager → SDK Tools →
  Google USB Driver;
- сменить USB-кабель;
- переключить в настройках телефона USB-режим на «Передача файлов».

### 4.3. Запустить приложение на телефоне

Из папки `mobile/`:

```powershell
flutter run                          # автоматически выберет подключенный
                                     # телефон если он единственный
# или явно указать:
flutter run -d <device-id-из-flutter-devices>
```

Первая сборка займёт 3–7 минут (компиляция Isar C++ библиотек под ARM).
Приложение установится на телефон и запустится автоматически.

### 4.4. Собрать отдельный APK и установить вручную (без USB)

```powershell
flutter build apk --release
```

Готовый APK: `mobile/build/app/outputs/flutter-apk/app-release.apk`.
Скиньте его на телефон (Google Drive, Telegram, USB), откройте с
телефона — Android предложит установить (нужно разрешить «установку из
неизвестных источников»).

## 4A. Установка и запуск на iOS (Mac + Xcode)

Сборка и запуск на iOS **возможны только на Mac** (требование Apple —
Xcode работает только под macOS). Всё, что описано в § 1–3 про Flutter,
build_runner и бэкенд, актуально и здесь один в один — отличаются только
инструменты платформы и способ запуска.

### 4A.1. Что установить на Mac

| Инструмент | Версия | Для чего |
|---|---|---|
| **Xcode** | последняя из App Store | Компилятор, симуляторы iOS, подпись приложения |
| **Xcode Command Line Tools** | вместе с Xcode | `xcodebuild`, `git` и т.д. |
| **CocoaPods** | последняя | Менеджер зависимостей для `ios/` (Isar, dio и др. тянут нативный код) |
| **Flutter SDK** | 3.24+ | Сборка мобильного приложения (тот же SDK, что и для Android) |
| **Docker Desktop / JDK 17+** | — | Если хотите поднять бэкенд на этом же Mac — см. § 2 |

Проверка:

```bash
xcodebuild -version              # должна показать версию Xcode
xcode-select -p                  # путь к Command Line Tools
flutter --version
flutter doctor -v                # покажет чего не хватает
pod --version
```

Если `xcode-select -p` ругается — установить Command Line Tools:

```bash
xcode-select --install
```

Если Xcode ставился впервые — открыть его один раз вручную и принять
лицензию (или из терминала):

```bash
sudo xcodebuild -license accept
```

CocoaPods, если не установлен:

```bash
brew install cocoapods
# или, если нет Homebrew:
sudo gem install cocoapods
```

`flutter doctor` должен показать зелёные галочки как минимум у пунктов
«Flutter», «Xcode - develop for iOS and macOS» и «CocoaPods». Пункты про
Android/Chrome для iOS-сборки не важны.

### 4A.2. Установить зависимости проекта

Из папки `mobile/` (то же самое, что и в § 3.1 — если уже делали для
Android, повторять не нужно):

```bash
cd mobile
flutter pub get
dart run build_runner build --delete-conflicting-outputs
```

Затем поставить нативные iOS-зависимости через CocoaPods:

```bash
cd ios
pod install
cd ..
```

`flutter run`/`flutter build ios` обычно делают `pod install` сами при
необходимости, но если видите ошибки про `.xcworkspace` или
«CocoaPods could not find compatible versions» — прогнать `pod install`
вручную ещё раз (иногда помогает `pod repo update` перед этим).

### 4A.3. Запуск в симуляторе iOS (самый быстрый способ проверить UI)

Открыть/выбрать симулятор:

```bash
open -a Simulator                # запустит симулятор с последним использованным устройством
xcrun simctl list devices        # список всех доступных симуляторов и их ID
```

Если нужного устройства нет в списке — создать через Xcode → Window →
Devices and Simulators → Simulators → «+».

Запустить приложение:

```bash
flutter devices                  # проверить, что симулятор виден Flutter'у
flutter run                      # выберет симулятор, если он единственный запущенный
# или явно:
flutter run -d <device-id-из-flutter-devices>
```

**Важно про адрес бэкенда.** Android-эмулятор обращается к хост-машине
через `10.0.2.2` — это значение стоит по умолчанию в
`lib/core/env.dart`. Симулятор iOS работает иначе: он выполняется на
самом Mac и видит `localhost` хоста напрямую. Если бэкенд поднят на
этом же Mac (§ 2), запускайте с переопределением адреса:

```bash
flutter run --dart-define=API_BASE_URL=http://localhost:8080
```

Иначе приложение будет пытаться достучаться до `10.0.2.2:8080`, которого
на iOS просто не существует, и синхронизация (Этап 4) не заработает —
офлайн-функциональность (Этапы 1–3) при этом всё равно будет работать
нормально.

### 4A.4. Запуск на реальном iPhone

1. **Подключить iPhone к Mac** кабелем (или по Wi-Fi, если уже
   настраивали беспроводную отладку в Xcode).
2. **На iPhone** — при первом подключении появится диалог «Доверять
   этому компьютеру?» → «Доверять» → ввести код-пароль.
3. **iOS 16+: включить Режим разработчика** (Developer Mode), если ещё
   не включён: Настройки → Конфиденциальность и безопасность → Режим
   разработчика → включить → телефон попросит перезагрузиться →
   подтвердить включение после перезагрузки.
4. **Настроить подпись приложения в Xcode** (обязательно для запуска на
   физическом устройстве — Apple требует подписанную сборку):
   ```bash
   open ios/Runner.xcworkspace
   ```
   В Xcode: выбрать таргет **Runner** → вкладка **Signing & Capabilities**
   → **Team** — выбрать свой Apple ID (если его нет в списке — Xcode →
   Settings → Accounts → «+» → войти с обычным Apple ID, платный
   Apple Developer аккаунт для запуска на своём устройстве не нужен,
   достаточно бесплатного). Bundle Identifier сейчас стоит
   `com.example.mymoney` — Xcode может попросить сменить его на уникальный
   (например `com.<ваш-ник>.mymoney`), если бесплатный аккаунт не даёт
   зарезервировать `com.example.*`.
5. **Запустить**:
   ```bash
   flutter devices                     # телефон должен появиться в списке
   flutter run -d <device-id>
   ```
   Первая сборка занимает несколько минут (компиляция нативных плагинов).
   При первом запуске на телефоне появится алерт «Ненадёжный
   разработчик» — это нормально, разрешается на следующем шаге.
6. **Если приложение установилось, но не открывается** («Untrusted
   Developer»): на iPhone — Настройки → Основные → VPN и управление
   устройством → выбрать профиль разработчика (ваш Apple ID) → «Доверять».

**Адрес бэкенда для реального iPhone** — как и с Android-телефоном (§ 4.1
там же по аналогии): `10.0.2.2` и `localhost` не подойдут, телефон и Mac
должны быть в одной Wi-Fi-сети, используйте LAN IP Mac'а:

```bash
flutter run -d <device-id> --dart-define=API_BASE_URL=http://192.168.x.y:8080
```

IP Mac'а можно узнать через Настройки → Wi-Fi → значок (i) рядом с сетью,
или `ipconfig getifaddr en0` в терминале.

### 4A.5. Сборка .ipa без запуска через Xcode (опционально)

Собрать release-сборку локально (без архивации под App Store/TestFlight,
только для проверки, что сборка проходит):

```bash
flutter build ios --release --no-codesign
```

Для полноценного `.ipa`, который можно поставить через TestFlight или
раздать по Ad Hoc, нужен платный Apple Developer Program (99$/год) и
архивация через Xcode (Product → Archive) — это уже относится к
дистрибуции, а не к локальному тестированию, и здесь не описывается.

## 5. Что тестировать вручную на смартфоне

Приложение работает **полностью офлайн** и **не хранит никаких аккаунтов**.
Каждая установка — отдельная «локальная семья». Поэтому сценарии простые.

### Приёмочный сценарий Этапа 1 (по § 24 Bible)

1. **Первый запуск.**
   Приложение открывается, показывает пустой экран «Главная», сумма
   баланса `0,00 ₽`.
   Проверка: при первом старте автоматически создались:
   - счёт «Наличные»;
   - все системные категории (проверить на вкладке «Операции» → добавить
     операцию — категории появятся списком).

2. **Добавить расход за ≤ 3 шага (ключевой DoD Этапа 1).**
   Нажать `+ Операция` внизу справа.
   - Шаг 1: тап по чипу счёта («Наличные»).
   - Шаг 2: тап по категории «Продукты».
   - Шаг 3: ввести сумму, например `500`, нажать «Сохранить».

   Приложение вернётся на предыдущий экран, операция появится в разделе
   «Последние операции» и в списке «Операции». Баланс на главной
   уменьшится на 500 ₽.

3. **Добавить доход.**
   `+ Операция` → переключить сегмент на «Доход» → выбрать «Зарплата» →
   ввести `50000` → сохранить. Баланс должен вырасти.

4. **Добавить новый счёт.**
   Вкладка «Счета» → `+` → название «Карта», тип «Карта», начальный
   баланс `10000` → «Сохранить». Он появится в списке; при добавлении
   следующей операции он появится как вариант выбора.

5. **Удалить операцию.**
   Вкладка «Операции» → свайп операции влево → подтвердить удаление.
   Баланс на главной пересчитается автоматически.

6. **Проверка Offline First (обязательный тест DoD).**
   Включить **режим полёта** на телефоне. Полностью закрыть и снова
   открыть приложение. Все данные должны быть на месте, добавление и
   удаление операций должно работать без ошибок и задержек.

7. **Проверка холодного старта.**
   Полностью закрыть приложение, снова открыть. Все счета/операции —
   на месте (данные лежат в локальном Isar).

Если хотите начать с нуля — «Приложения» → MyMoney → «Очистить
данные», перезапустить: снова seed'нутся системные категории и «Наличные».

### Приёмочный сценарий Этапа 2 — планирование (по § 24 Bible)

Всё также работает **офлайн**; бэкенд-часть Этапа 2 существует
параллельно и подключится к клиенту в Этапе 4.

**Бюджет** — вкладка «Бюджет».

1. Нажать `+` (правый нижний угол) → выбрать категорию расходов
   (например «Продукты»), период «Месяц», ввести план `20000` →
   «Сохранить». Появится карточка с прогресс-баром.
2. Перейти на «Операции» → добавить расход в той же категории на
   `500 ₽`. Вернуться на «Бюджет» — прогресс-бар должен вырасти,
   «Потрачено» = 500 ₽, «Осталось» уменьшилось на 500 ₽.
3. Добавить расход, превышающий план. Полоска станет красной,
   строка сменится на «Превышение на … ₽».
4. Тап по карточке — открывается лист с редактированием суммы плана
   (категорию/период менять запрещено — они образуют идентичность
   бюджета).
5. Длинный тап по карточке — удаление.

**Цели** — вкладка «Цели».

1. `+` → название «Отпуск», целевая сумма `100000`, опционально дата →
   «Сохранить».
2. На карточке — кнопка «Пополнить» → ввести `20000`. Прогресс-бар
   вырастет до 20%.
3. Кнопка «Снять» → нельзя увести в минус (клиент молча блокирует).
4. При достижении цели рядом с названием появляется галочка ✓.
5. Тап по карточке — редактирование, длинный тап — удаление.

### Приёмочный сценарий Этапа 3 — аналитика (по § 24 Bible)

Всё также работает **офлайн**. Статистика собирается исключительно из локальных данных Isar.

**Аналитика** — вкладка «Статистика» (иконка графика).

1. По умолчанию показывает отчёт за **текущий месяц**.
2. Переключение периода: нажать на сегментированный контроль — выбрать «Неделя», «Месяц» или «Год». Диаграмма перестраивается.
3. Карточки в верхней части показывают:
   - Доход за период
   - Расход за период
   - Остаток (доход − расход)
4. Круговая диаграмма (pie chart) — распределение расходов по категориям, каждый сегмент — процент от всех трат за период.
5. Таблица ниже диаграммы — расходы по категориям в руб. и %, отсортированы по убыванию суммы.
6. Если есть бюджеты на период — таблица «Сравнение с бюджетом» показывает:
   - План на категорию
   - Потрачено в действительности
   - Статус («В норме» / «Превышено»)
   - Прогресс-бар (зелёный если в норме, красный если превышено)
7. Кнопка «Экспортировать PDF» → генерирует отчёт и предлагает поделиться (Email, Google Drive, облако и т.д.).

**Проверка:**
1. Добавить несколько операций разных категорий в «Операции».
2. Перейти на вкладку «Статистика» — диаграмма должна показать все категории.
3. Переключить период «Неделя/Месяц/Год» — каждый раз пересчитывается только то, что попало в окно.
4. Экспортировать PDF → проверить, что файл содержит верные суммы, названия категорий, дату отчёта.

## 7. Возможные проблемы и решения

| Симптом | Решение |
|---|---|
| `docker compose` ругается на порт `5432` | Порт уже занят — сменить `POSTGRES_PORT` в `.env` (и порт в `DB_URL`!) или погасить того, кто занял |
| **`FATAL: role "mymoney" does not exist`, хотя контейнер `healthy`** | Классика: `localhost:5432` уходит в нативный Postgres мимо контейнера. Полный разбор — § 2.2 |
| `{"status":"ok","db":"down"}` от `/healthz` | Сервер жив, базу не видит. Проверить `docker compose ps` и совпадение порта в `DB_URL` с `POSTGRES_PORT` |
| «Порт 8080 занят», хотя Gradle остановлен | Сервер — потомок Gradle-демона и пережил Ctrl+C. `./scripts/run-backend.sh stop` или `lsof -nP -iTCP:8080 -sTCP:LISTEN` + `kill` |
| `zsh: permission denied: ./gradlew` | `chmod +x backend/gradlew` (бит `+x` теряется при клонировании) |
| `JAVA_HOME is not set` / собирается не той Java | macOS: `export JAVA_HOME="$(/usr/libexec/java_home -v 17)"` |
| `Cannot connect to the Docker daemon` | Docker установлен, но не запущен. macOS: открыть Docker.app и дождаться зелёного индикатора |
| PowerShell: «выполнение сценариев отключено» | `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned` |
| Первый `./gradlew run` очень долгий | Нормально, скачиваются Kotlin/Ktor/Exposed |
| Поменяли `POSTGRES_USER`/`PASSWORD`, база не пускает | Учётка создаётся только при первой инициализации volume. Пересоздать: `docker compose down && docker volume rm mymoney-postgres-data` (**удалит данные**) |
| Backend не стартует, ругается на JDBC | Проверить, что Postgres запущен (`docker compose ps`) и `DB_URL` в `.env` корректен |
| Flutter: «Target of URI not found: '…entity.g.dart'» | Не запущен build_runner — выполнить `dart run build_runner build --delete-conflicting-outputs` |
| `flutter devices` не видит телефон | USB-режим «Передача файлов» + переустановить Google USB Driver через Android Studio |
| Приложение падает при первом запуске | Проверить, что в pubspec есть `isar_flutter_libs` и что дал разрешение на запись хранилища |
| На главной пусто, но кнопка «+ Операция» не работает | Проверить, что seed прошёл: удалить данные приложения через Настройки → Приложения → MyMoney и перезапустить |
| `pod install` падает с ошибкой версий/репозитория | `pod repo update`, затем повторить `pod install`; убедиться, что CocoaPods обновлён (`brew upgrade cocoapods`) |
| Xcode: «No account for team» / ошибка подписи | Xcode → Settings → Accounts → добавить Apple ID; в Runner → Signing & Capabilities выбрать Team |
| На iPhone приложение не открывается, «Untrusted Developer» | Настройки → Основные → VPN и управление устройством → довериться профилю разработчика |
| Симулятор iOS не виден в `flutter devices` | `open -a Simulator`, дождаться полной загрузки, затем повторить `flutter devices` |
| Синхронизация (Этап 4) не работает на iOS, хотя офлайн-функции ок | Проверить `API_BASE_URL`: на симуляторе нужен `http://localhost:8080`, на реальном iPhone — LAN IP Mac'а (`10.0.2.2` работает только для Android-эмулятора) |

## 9. Ручная приёмка Этапа 4 (семья + синхронизация)

Требует запущенного бэкенда (см. §2). Мобильное приложение по умолчанию
обращается к `http://10.0.2.2:8080` — это адрес хостовой машины из
Android-эмулятора. На реальном телефоне нужно вписать локальный IP ПК:
`http://192.168.x.y:8080` (телефон и ПК в одной Wi-Fi-сети).

Сценарии:

**Регистрация и первый sync.**

Авторизация обязательна: без сессии приложение открывает онбординг и дальше
«Добро пожаловать» не пускает.

1. Запустить приложение → экран «Добро пожаловать» → «Создать аккаунт».
2. Ввести email + пароль (≥ 8 символов). Кнопка активна только когда
   индикатор надёжности жёлтый или зелёный.
3. Экран «Подтвердите почту». Код взять из лога бэкенда — строка
   `[DEV] Email confirmation code for ... is NNNNNN`.
4. Ввести 6 цифр → «Аккаунт успешно создан» → «Перейти в приложение».
5. Локальный Isar очищается, стартует первый pull → на вкладке «Категории»
   появляется серверный seed.
6. Открыть «Настройки» → раздел «Синхронизация» → должна быть
   заполнена «Последняя синхронизация».

**Вход существующим аккаунтом.** «Добро пожаловать» → «У меня уже есть
аккаунт». Если почта так и не подтверждена, бэкенд ответит
`EMAIL_NOT_VERIFIED`, приложение само вышлет новый код и откроет экран
подтверждения.

**Выход.** «Настройки» → «Выйти» — приложение возвращается на онбординг.

**Ручная синхронизация.**
1. Создать пару операций локально.
2. «Настройки» → «Синхронизировать сейчас» → SnackBar показывает
   `pushed=N, pulled=M, conflicts=0`.

**Приглашение в семью (двух пользователей).**
1. С устройства A (owner): «Настройки» → «Управление семьёй» → ввести
   email пользователя B → «Создать приглашение» → нажать «Скопировать».
2. С устройства B (только что зарегистрированного): «Настройки» →
   «Управление семьёй» → вставить токен в поле «Принять приглашение»
   → «Принять».
3. Приложение B выйдет из учётной записи (сервер отозвал refresh).
   Заново войти с email B — теперь `familyId` совпадает с A.
4. После sync на B должны появиться операции A. Изменения B тоже
   пропишутся в семью A после его следующего push.

**Проверка LWW-конфликтов.**
1. Устройство A изменяет операцию X → «Синхронизировать сейчас».
2. Устройство B (без предварительного pull) редактирует ту же X →
   «Синхронизировать сейчас».
3. Ожидание: B получает `conflicts=1`. Локальная версия B перезаписывается
   на серверную (версию A). Проверить, что старая версия B видна
   в истории (когда UI истории будет добавлен на дальнейших этапах).
