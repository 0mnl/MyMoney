## Как читать этот документ

Документ описывает **все пользовательские сценарии MVP** приложения MyMoney — по одной записи на каждый прецедент, а также **все экраны мобильного клиента** и **все эндпоинты бэкенда**, обеспечивающие эти сценарии.

Каждый use case имеет структуру:

- **ID** — уникальный идентификатор (UC-XX).
- **Актор** — кто выполняет.
- **Предусловия** — что должно быть верным до старта.
- **Основной сценарий** — happy path.
- **Альтернативные сценарии** — отклонения (ошибки, отмена, повтор).
- **Постусловия** — состояние системы после успешного завершения.
- **Точка входа (UI)** — экран/кнопка мобильного клиента.
- **Точка входа (API)** — эндпоинт бэкенда.

Идентификаторы UC-01..UC-08 сохранены из Bible v2 §8; UC-09 и далее — расширение под фактический скоуп.

---

## 1. Акторы

| Актор | Описание |
|---|---|
| **Гость** | Пользователь без активной сессии. Доступны только регистрация и логин. |
| **Пользователь** | Аутентифицированный владелец аккаунта. Одновременно является участником своей семьи (роль `OWNER`). |
| **Участник семьи** | *Пост-MVP.* Пользователь, принявший приглашение в чужую семью (роль `MEMBER`). В MVP не используется — семейный бюджет исключён (Bible v2 §6, §21). |
| **Клиент (мобильное приложение)** | Автономный актор синхронизации — выполняет фоновые push/pull без явных действий пользователя. |
| **Администратор системы** | Обслуживает сервер. **Не имеет доступа** к содержимому финансовых данных (принцип Bible v2 §15). |

---

## 2. Домены и модули

Функциональность разделена на домены, соответствующие Bible v2 §6:

1. **Auth** — регистрация, вход, обновление токена, выход со всех устройств.
2. **Accounts** — счета (включая **credit_limit** для кредитных карт, Bible v2 §7.2).
3. **Categories** — категории (системные + пользовательские, двухуровневые).
4. **Transactions** — операции (доход/расход/перевод) с audit trail.
5. **Budgets** — плановые бюджеты (неделя/месяц/год).
6. **Goals** — накопительные цели.
7. **Debts** — учёт долгов **с процентами и графиком платежей** (`DebtPayment`, Bible v2 §7.7, §13).
8. **Subscriptions** — регулярные платежи.
9. **Family** — *пост-MVP.* Совместный бюджет до 2 участников исключён из MVP (Bible v2 §21). Таблицы `family` / `family_member` сохраняются как контейнер данных (принцип 10.3), приглашения `family_invite` — в коде, но UC MVP не покрывает.
10. **Sync** — фоновая двухсторонняя синхронизация с сервером (LWW).
11. **Analytics & Export** — круговая аналитика и PDF-выгрузка.

## 3. Каталог Use Cases

### 3.1 Auth (UC-01, UC-02, UC-09, UC-10)

---

#### UC-01 — Регистрация нового пользователя

- **Актор:** Гость.
- **Предусловия:** Приложение запущено, интернет доступен. E-mail ранее не использовался.
- **Основной сценарий:**
  1. Пользователь открывает `LoginScreen`, переключает режим на «Регистрация».
  2. Вводит e-mail и пароль (минимальные требования валидируются локально).
  3. Нажимает «Зарегистрироваться».
  4. Клиент вызывает `POST /auth/register` с `{ email, password }`.
  5. Сервер: `EmailValidator` проверяет формат; `RegisterUserUseCase` создаёт запись в `app_user` (пароль — argon2id), создаёт новую `family` и `family_member` с ролью `OWNER`.
  6. Сервер возвращает `{ userId, familyId }`.
  7. Клиент немедленно выполняет UC-02 (авто-логин).
- **Альтернативные сценарии:**
  - **E-mail занят** → сервер возвращает `409`, клиент показывает ошибку без сброса полей.
  - **Невалидный e-mail/пароль** → локальная валидация, запрос не уходит.
  - **Нет сети** → снекбар «Требуется подключение к интернету для регистрации».
- **Постусловия:** Создан пользователь, его собственная семья, `OWNER`-мембершип. Сессия начата.
- **UI:** `LoginScreen` (`mobile/lib/presentation/screens/login_screen.dart`).
- **API:** `POST /auth/register`.

---

#### UC-02 — Вход в аккаунт

- **Актор:** Гость.
- **Предусловия:** Аккаунт зарегистрирован. Интернет доступен.
- **Основной сценарий:**
  1. Пользователь вводит e-mail и пароль в `LoginScreen`, нажимает «Войти».
  2. `authenticateAndSyncProvider` вызывает `POST /auth/login`.
  3. Сервер `LoginUseCase` проверяет пароль, находит `family_id` пользователя, создаёт refresh-токен в `refresh_token` с уникальным `jti`.
  4. Сервер возвращает `{ accessToken, refreshToken, userId, familyId }`.
  5. Клиент сохраняет токены в secure storage, очищает локальный Isar (если это другой аккаунт), запускает **первичную полную синхронизацию** (UC-24).
  6. По завершении навигация на `HomeShell`.
- **Альтернативные сценарии:**
  - **Неверные креды** → `401`, форма подсвечивает ошибку.
  - **Нет сети** → отказ, пользователь остаётся на `LoginScreen`.
  - **Первый вход на устройстве** → seed системных категорий из `SystemCategoriesCatalog` (см. UC-11 подсценарий).
- **Постусловия:** Активная JWT-сессия. Локальный Isar заполнен данными семьи.
- **UI:** `LoginScreen`.
- **API:** `POST /auth/login`.

---

#### UC-09 — Обновление access-токена

- **Актор:** Клиент (автоматически, без участия пользователя).
- **Предусловия:** Есть валидный refresh-токен; access-токен истёк.
- **Основной сценарий:**
  1. Dio-интерцептор ловит `401` на любом запросе.
  2. Клиент вызывает `POST /auth/refresh` с текущим `refreshToken`.
  3. Сервер `RefreshTokenUseCase` проверяет `refresh_token.revoked_at IS NULL`, ротирует токен (старый помечает `revoked_at`, выдаёт новый), возвращает пару.
  4. Клиент повторяет исходный запрос с новым access-токеном.
- **Альтернативные сценарии:**
  - **Refresh-токен отозван/истёк** → сервер возвращает `401`; клиент выполняет UC-10 (принудительный выход) и открывает `LoginScreen`.
- **Постусловия:** Сессия продлена, старый refresh-токен отозван.
- **API:** `POST /auth/refresh`.

---

#### UC-10 — Выход со всех устройств

- **Актор:** Пользователь.
- **Предусловия:** Активная сессия.
- **Основной сценарий:**
  1. На `SettingsScreen` пользователь нажимает «Выйти со всех устройств».
  2. Клиент вызывает `POST /auth/logout-all` с текущим access-токеном.
  3. Сервер `LogoutAllUseCase` помечает все `refresh_token.revoked_at = NOW()` для `user_id`.
  4. Клиент очищает local secure storage и Isar, переходит на `LoginScreen`.
- **Альтернативные сценарии:**
  - **Нет сети** → сервер не оповещён; клиент всё равно локально разлогинивается, но токены на других устройствах остаются валидными до истечения. Пользователю показывается предупреждение.
- **Постусловия:** Все refresh-токены пользователя отозваны; локальное состояние сброшено.
- **UI:** `SettingsScreen`.
- **API:** `POST /auth/logout-all`.

### 3.2 Accounts (UC-11..UC-15)

---

#### UC-11 — Создание счёта

- **Актор:** Пользователь.
- **Предусловия:** Активная сессия.
- **Основной сценарий:**
  1. На `AccountsScreen` нажимает FAB «+».
  2. Диалог: имя, тип (свободный текст), начальный баланс в рублях, **опционально — лимит кредитной карты** (`credit_limit`, Bible v2 §7.2). Поле показывается только когда тип соответствует кредитному счёту.
  3. Клиент конвертирует сумму(-ы) в копейки (`amount * 100`), генерирует UUID, вызывает `CreateAccountUseCase` (локально): сохраняет `AccountEntity` в Isar с флагами `isDirty=true`, `localVersion=1`.
  4. UI обновляется немедленно из `accountsStreamProvider`.
  5. `SyncScheduler` в фоне отправит запись через `POST /sync/push` → сервер создаёт строку в таблице `account`.
- **Правила:** Доступный остаток по кредитке = `credit_limit − сумма непогашенных расходов по счёту` (Bible v2 §7.2).
- **Альтернативные сценарии:**
  - **Пустое имя** → форма не отправляется.
  - **Оффлайн** → работает как обычно; синхронизация произойдёт при восстановлении сети.
- **Постусловия:** Счёт виден в списке, участвует в расчёте общего баланса.
- **UI:** `AccountsScreen` → диалог «Новый счёт».
- **API:** `POST /accounts` (или через `POST /sync/push` для фоновой отправки).

---

#### UC-12 — Просмотр списка счетов

- **Актор:** Пользователь.
- **Предусловия:** —
- **Основной сценарий:**
  1. Пользователь открывает `AccountsScreen`.
  2. `accountsStreamProvider` возвращает список из Isar (`is_deleted=false`).
  3. Каждый счёт отображается с текущим балансом (initial_balance + сумма всех операций счёта).
  4. Общий баланс семьи виден также на `HomeTab`.
- **Альтернативные сценарии:**
  - **Показать архивные** → тумблер «Включая архивные» в AppBar, клиент передаёт `includeArchived=true` в `list`-запрос.
- **Постусловия:** —
- **UI:** `AccountsScreen`, `HomeTab`.
- **API:** `GET /accounts?includeArchived=<bool>` (при синхронизации).

---

#### UC-13 — Редактирование счёта

- **Актор:** Пользователь.
- **Основной сценарий:** Открытие карточки счёта → изменение имени/типа/начального баланса → сохранение → локальное обновление + фоновая `PUT /accounts/{id}`.
- **Альтернативные сценарии:** Конфликт при sync → см. UC-25.
- **API:** `PUT /accounts/{id}`.

---

#### UC-14 — Архивирование счёта

- **Актор:** Пользователь.
- **Основной сценарий:** Свайп/меню на карточке → «Архивировать» → `is_archived=true`. Счёт исчезает из основного списка, но история операций сохраняется.
- **Постусловия:** Счёт не участвует в общем балансе, операции по нему остаются видимыми в аналитике.
- **API:** `POST /accounts/{id}/archive`.

---

#### UC-15 — Удаление счёта (soft delete)

- **Актор:** Пользователь.
- **Предусловия:** По счёту нет незакрытых обязательных связей (в MVP — проверка не строгая).
- **Основной сценарий:** Меню → «Удалить» → подтверждение → `is_deleted=true`. Синхронизация распространяет удаление на другие устройства.
- **Альтернативные сценарии:** Отмена — стандартный кнопка «Отмена» в диалоге.
- **Постусловия:** Счёт скрыт везде; физически данные не удаляются (нужны для audit trail и sync).
- **API:** `DELETE /accounts/{id}`.

### 3.3 Categories (UC-16..UC-19)

---

#### UC-16 — Инициализация системных категорий

- **Актор:** Клиент (автоматически при первом входе).
- **Основной сценарий:**
  1. После UC-02 `bootstrapProvider` проверяет наличие категорий в Isar для текущей `familyId`.
  2. Если категорий нет — вызывает `SeedSystemCategoriesUseCase`, который создаёт около 30–40 предустановленных категорий из `SystemCategoriesCatalog` (Продукты, Транспорт, Жильё, Зарплата и др.) с флагами `is_system=true`, `is_mandatory` в зависимости от типа.
  3. Категории двухуровневые: родительские категории с подкатегориями (`parent_category_id`).
- **Постусловия:** Семья имеет базовый набор категорий, готовых к использованию.

---

#### UC-17 — Создание пользовательской категории

- **Актор:** Пользователь.
- **Основной сценарий:**
  1. В `AddTransactionScreen` (или в отдельном разделе управления) выбирает «+ Новая категория».
  2. Указывает имя, тип (INCOME/EXPENSE), родительскую категорию (опционально), иконку, цвет, флаг «обязательная».
  3. Клиент сохраняет `CategoryEntity` с `is_system=false`.
- **Альтернативные сценарии:** Родитель — только категория того же типа (INCOME↔INCOME).
- **API:** `POST /categories`.

---

#### UC-18 — Редактирование категории

- **Актор:** Пользователь.
- **Основной сценарий:** Открытие категории → правка полей → сохранение.
- **Особенности:**
  - Системные категории **редактируемы** (можно переименовать, изменить иконку/цвет, признак обязательности), но **не удаляемы физически** (см. UC-19).
- **API:** `PUT /categories/{id}`.

---

#### UC-19 — Архивирование / удаление категории

- **Актор:** Пользователь.
- **Основной сценарий:**
  - **Системная категория** → доступно только архивирование (`is_archived=true`), физическое удаление запрещено на уровне бизнес-правил (закрытие открытого вопроса №5 Bible).
  - **Пользовательская категория** → доступно и архивирование, и soft delete (`is_deleted=true`).
- **Альтернативные сценарии:** Категория используется в бюджете/подписке — предупреждение, пользователь подтверждает или отменяет.
- **API:** `POST /categories/{id}/archive`, `DELETE /categories/{id}`.

### 3.4 Transactions (UC-03, UC-04, UC-20..UC-23)

Центральный домен приложения. Bible §8: **≤ 3 шага, < 10 секунд** на добавление операции.

---

#### UC-03 — Добавление расхода

- **Актор:** Пользователь.
- **Предусловия:** Есть хотя бы один счёт и хотя бы одна EXPENSE-категория.
- **Основной сценарий (целевые 3 шага):**
  1. **Шаг 1:** На `HomeTab` или `TransactionsScreen` нажимает FAB «−» (расход). Открывается `AddTransactionScreen` с типом = EXPENSE. Выбор счёта (по умолчанию — активный/последний использованный).
  2. **Шаг 2:** Выбор категории из списка (двухуровневый: сначала родитель → подкатегория, либо один клик по подкатегории).
  3. **Шаг 3:** Ввод суммы; дата по умолчанию — сейчас, комментарий и фото — опционально.
  4. Нажатие «Сохранить» → клиент генерирует UUID, конвертирует сумму в копейки, сохраняет `TransactionEntity` в Isar. UI сразу обновляется.
  5. `SyncScheduler` в фоне отправляет операцию через `POST /sync/push`.
- **Альтернативные сценарии:**
  - **Прикрепить фото** → выбор источника (камера/галерея), путь к файлу сохраняется в `attachment_photo_path`. **OCR отсутствует** — только вложение.
  - **Изменить дату** → date-picker для прошедших операций.
  - **Отмена** → возврат назад без сохранения.
- **Постусловия:** Операция видна в списке операций, отражена в балансе счёта, учтена в бюджете и аналитике.
- **UI:** `AddTransactionScreen` (`add_transaction_screen.dart`).
- **API:** `POST /transactions`.

---

#### UC-04 — Добавление дохода

Полностью аналогично UC-03, но `type = INCOME`, FAB «+» и выбор из INCOME-категорий.

---

#### UC-20 — Добавление перевода между счетами

- **Актор:** Пользователь.
- **Предусловия:** Не менее двух активных счетов.
- **Основной сценарий:**
  1. В `AddTransactionScreen` выбирает тип TRANSFER.
  2. Указывает счёт-источник, счёт-получатель, сумму, дату.
  3. Клиент проверяет через `TransactionValidation`: `source ≠ target`, оба не архивированы, `target_account_id` не null.
  4. Сохранение — одна `TransactionEntity` типа TRANSFER с `target_account_id`.
- **Особенности:** В балансе исходный счёт уменьшается, целевой увеличивается; в аналитике по категориям расхода перевод не учитывается.
- **API:** `POST /transactions` с `type=TRANSFER`.

---

#### UC-21 — Просмотр списка операций

- **Актор:** Пользователь.
- **Основной сценарий:** `TransactionsScreen` показывает список из Isar, отсортированный по `occurred_at DESC`. Каждая строка: иконка/цвет категории, название категории, счёт, сумма (красный для расхода, зелёный для дохода), дата.
- **Альтернативные сценарии:**
  - **Фильтр по счёту/категории/периоду** → передача параметров в `ListTransactionsUseCase` (query-параметры `accountId`, `categoryId`, `from`, `to`).
  - **Пагинация** → `limit`/`offset`.
- **UI:** `TransactionsScreen`.
- **API:** `GET /transactions?...`.

---

#### UC-22 — Редактирование операции с сохранением истории

- **Актор:** Пользователь.
- **Основной сценарий:**
  1. Открытие карточки операции → правка сумма/категория/счёт/комментарий → «Сохранить».
  2. `UpdateTransactionUseCase` на сервере **до** обновления записи копирует текущее состояние в `transaction_history` (`snapshot_json`) с указанием `changed_by`, `changed_at`.
  3. Обновляется основная запись, `updated_at` меняется.
- **Постусловия:** Аудит-цепочка операции пополнилась одним снимком.
- **API:** `PUT /transactions/{id}`.

---

#### UC-23 — Просмотр истории изменений операции

- **Актор:** Пользователь.
- **Основной сценарий:** В карточке операции — кнопка «История изменений». Клиент запрашивает `GET /transactions/{id}/history`, показывает список снимков (кто, когда, какие поля).
- **API:** `GET /transactions/{id}/history`.

---

### 3.5 Budgets (UC-05, UC-26..UC-28)

---

#### UC-05 — Создание бюджета

- **Актор:** Пользователь.
- **Основной сценарий:**
  1. `BudgetsScreen` → «+» → выбор периода (WEEK/MONTH/YEAR), начала периода, категории (EXPENSE), планового лимита в рублях.
  2. Клиент конвертирует в копейки, сохраняет `BudgetEntity`.
- **Правила:**
  - Единая сущность Budget; «смета» реализована через флаг `is_mandatory` на категории (закрытие открытого вопроса №7 Bible).
- **API:** `POST /budgets`.

---

#### UC-26 — Просмотр бюджета с прогрессом

- **Актор:** Пользователь.
- **Основной сценарий:**
  1. `BudgetsScreen` показывает активные бюджеты за выбранный период карточками.

#### UC-07 — Приглашение участника в семью *(пост-MVP)*

#### UC-38 — Принятие приглашения *(пост-MVP)*

### 3.10 Sync (UC-24, UC-25)

---

#### UC-24 — Полная синхронизация с сервером (push + pull)

- **Актор:** Клиент (SyncManager, автоматически).
- **Триггеры:**
  - Логин (первичная синхронизация).
  - Открытие `HomeShell` (`SyncScheduler`).
  - Периодически в фоне.
  - После любой локальной операции (отложенно).
- **Основной сценарий:**
  1. **Push:** SyncManager собирает все `is_dirty=true` записи всех коллекций Isar → `POST /sync/push`.
  2. Сервер `PushChangesUseCase` для каждой записи: если её `updated_at` >= серверной или запись новая → upsert; иначе — фиксирует конфликт.
  3. Ответ: `{ accepted: [...], conflicts: [...] }`. Клиент для конфликтов сохраняет свою (проигравшую) версию в локальный `transaction_history`-эквивалент и принимает серверную.
  4. Клиент помечает принятые записи `is_dirty=false`, `last_synced_at=<serverTime>`.
  5. **Pull:** Клиент вызывает `GET /sync/pull?since=<last_synced_at>`.
  6. Сервер возвращает все записи, изменённые после cursor'а, плюс `serverTime`.
  7. Клиент выполняет upsert локально, сохраняет новый cursor.
- **Альтернативные сценарии:**
  - **Нет сети** → цикл пропускается, повтор при следующем триггере.
  - **`401` на push/pull** → срабатывает UC-09 (refresh), повтор.
- **Постусловия:** Локальный Isar и сервер согласованы по состоянию на `serverTime`.
- **API:** `POST /sync/push`, `GET /sync/pull`.

---

#### UC-25 — Разрешение конфликта синхронизации (Last-Write-Wins)

- **Актор:** Клиент (автоматически, в рамках UC-24).
- **Основной сценарий:**
  1. Два устройства редактируют одну операцию офлайн.
  2. Устройство A первым выполняет push → сервер принимает.
  3. Устройство B выполняет push → сервер видит, что его `updated_at` **старше** серверного → отвечает конфликтом с текущей серверной версией.
  4. B сохраняет свою локальную версию в `transaction_history` (audit-снимок), локальную запись заменяет серверной.
  5. Пользователь на B при просмотре истории операции видит обе версии.
- **Правило:** LWW по `updated_at`, проигравшая версия не теряется.
- **Постусловия:** Данные согласованы; ни одна версия не потеряна.

## 6. Cross-cutting поведения

### 6.1 Offline First
- Все read-операции на клиенте — из Isar; сеть не запрашивается.
- Все write-операции — сначала в Isar, немедленное обновление UI; синхронизация — асинхронно.
- Приложение полностью работоспособно в авиарежиме.

### 6.2 Деньги
- Хранение — целые числа в **копейках** (`BIGINT` на сервере, `int64` на клиенте).
- Форматирование в рубли — только на уровне presentation.

### 6.3 Валюта
- MVP: только `RUB`. Поле `currency` присутствует в схеме для будущей мультивалютности.

### 6.4 Мягкое удаление
- Все пользовательские сущности имеют `is_deleted`. Физическое удаление запрещено (нужно для sync).

### 6.5 Audit trail
- Изменения операций пишутся в `transaction_history` (JSONB на сервере). Проигравшая версия конфликта тоже туда попадает.

### 6.6 Безопасность
- Пароли: argon2id.
- Refresh-токены: хэш в БД, уникальный `jti`, `revoked_at` для logout-all.
- Транспорт: TLS. Клиент передаёт `Authorization: Bearer <access>`.
- Администратор не имеет функциональных прав на чтение содержимого финансов (архитектурный принцип Bible §13). *End-to-end шифрование данных на MVP не реализовано — задача пост-MVP.*

---

## 7. Definition of Done (напоминание из Bible §14)

Каждый Use Case из этого документа считается завершённым, только если реализованы **все пять** пунктов:

1. UI.
2. Бизнес-логика (use case-класс).
3. Локальное хранение (Isar).
4. Синхронизация (push/pull).
5. Тесты (unit + при необходимости widget/integration).

---

## 8. Ограничения MVP (не входит в use cases)

Явно исключено из MVP (Bible §5, §16), поэтому use cases для этих направлений **не разрабатываются**:

- OCR распознавание чеков.
- AI-категоризация.
- Инвестиции, акции, криптовалюты.
- Банковские API.
- Голосовой ввод, геолокация.
- Web / desktop / iOS.
- Telegram-бот.
- Импорт данных из внешних источников.
- Расширенная аналитика (прогнозирование, сравнение периодов и т. д.).
- Мультивалютность (готовность в схеме есть, use case — пост-MVP).
