## 1. Миссия и видение

### Проект

MyMoney — современная система управления личными и семейными финансами, ориентированная на максимально простой ежедневный учёт денежных средств, долгосрочное финансовое планирование и развитие финансовой дисциплины пользователя.

Проект задуман с расчётом на многолетнюю поддержку и потенциальную коммерциализацию в будущем, **но публикация MVP в Google Play / App Store не планируется** (см. раздел 6). Архитектура тем не менее проектируется без необходимости полного переписывания при масштабировании — это требование сохраняется независимо от планов публикации.

### Миссия

Создать простое, быстрое и надёжное приложение для ведения личного (и в перспективе — семейного) бюджета, которым удобно пользоваться ежедневно без специальных финансовых знаний.

### Видение (горизонт нескольких лет)

MyMoney должен стать экосистемой управления личными финансами:

- Android-приложение на старте, iOS — следующий этап после MVP;
- безопасная облачная синхронизация;
- совместный семейный бюджет (пост-MVP, см. раздел 21);
- накопительные цели;
- резервное копирование;
- интеллектуальная аналитика и OCR/AI-помощник (далёкое будущее).

### Главная идея

Большинство приложений учёта бюджета заставляют пользователя постоянно думать о самом приложении. MyMoney должен делать обратное — пользователь думает только о своих финансах, а не о том, как ими управлять в приложении.

**Основная цель проекта** — максимально уменьшить количество действий пользователя при сохранении высокой точности учёта финансов.

## 2. Философия продукта

### Чем MyMoney не является

- Не бухгалтерская система.
- Не система управления предприятием.
- Не банковское приложение.

MyMoney — **персональный финансовый помощник**.

### Ценности продукта

1. Пользователь всегда владеет своими данными.
2. Offline First — отсутствие интернета не должно блокировать работу.
3. Минимум действий для выполнения любой задачи.
4. Архитектура важнее быстрых временных решений.
5. Безопасность и надёжность — обязательные требования, а не опции.

### Приоритеты проекта

Простота → Скорость → Надёжность → Безопасность → Понятность.

### Ключевые принципы

| Принцип | Формулировка |
|---|---|
| Простота | Любое действие требует минимального количества нажатий |
| Скорость | Добавление новой операции — менее 10 секунд |
| Надёжность | Потеря пользовательских данных — критическая ошибка |
| Offline First | Приложение полностью функционирует без интернета |
| Владение данными | Экспорт данных никогда не ограничивается |

Интернет используется **только** для синхронизации, резервного копирования и регистрации. Всё остальное работает локально.

### Правило "можно ли быстрее"

При проектировании любого нового экрана задаётся вопрос: *«Можно ли сделать это быстрее?»* Если ответ «да» — интерфейс перерабатывается. Применяется на каждом ревью UI/UX перед принятием фичи.

## 3. Целевая аудитория

- Пользователи 18–45 лет.
- Люди, ведущие личный бюджет.
- Пользователи без бухгалтерского образования — интерфейс и терминология должны быть понятны без специальных знаний.

> Изменено относительно исходных документов: семейный бюджет исключён из MVP (см. раздел 6), поэтому «семьи из двух человек» больше не целевой сценарий *на этапе MVP* — это возвращается как аудитория при реализации фичи в будущем (раздел 21).

## 4. Принцип принятия решений

Центральный механизм разрешения споров при разработке — любое архитектурное или продуктовое решение проверяется в порядке приоритета:

1. **Быстрое решение vs правильная архитектура** → выбирается **архитектура**.
2. **Архитектура vs удобство пользователя** → выбирается **удобство пользователя**.

Для каждого решения дополнительно нужно ответить на 4 вопроса:

1. Улучшает ли оно пользовательский опыт?
2. Соответствует ли Offline First?
3. Не нарушает ли архитектуру?
4. Позволяет ли масштабировать проект в будущем?

Если хотя бы один ответ отрицательный — решение пересматривается.

> Поможет ли это сделать приложение проще, быстрее, надёжнее и удобнее через три года?

## 6. Границы MVP

### Входит в MVP

- Регистрация и авторизация (по e-mail, JWT)
- Локальное хранение данных (offline-first)
- Облачная синхронизация (single-user)
- Счета (с поддержкой лимита кредитной карты)
- Категории (двухуровневые, системные + пользовательские)
- Доходы и расходы
- Планирование бюджета
- Накопительные цели
- Долги (**с учётом процентов и графиком платежей** — см. раздел 20, п.7)
- Подписки (базовый учёт, без детализации уведомлений)
- Круговая аналитика (без трендов и сравнения периодов)
- Резервное копирование (через облачную синхронизацию)

### Не входит в MVP (перенесено в раздел 21)

- **Семейный бюджет** — исключён из MVP как pivot-решение (был в MVP в обоих исходных документах, но при слиянии зафиксировано обратное).
- iOS — доступен только Android на MVP.
- Инвестиции, криптовалюты, акции, банковские API.
- OCR чеков, AI-категоризация, голосовой ввод.
- Геолокация.
- Web-версия, Desktop, Telegram-бот.
- Импорт данных.
- Расширенная аналитика (тренды, сравнение периодов).
- Публикация в сторы и всё, что с ней связано (юридика, биллинг).
- Мультивалютность (только рубли на MVP).
- Тёмная тема, виджеты на главный экран, жесты, accessibility (VoiceOver/TalkBack).

### Платформы

MVP разрабатывается **только для Android** (мин. версия Android 8+). iOS — часть долгосрочного видения, но не MVP. Архитектура (Flutter + Clean Architecture, см. раздел 11) выбрана так, чтобы переход на iOS в будущем не требовал переписывания бизнес-логики.

## 7. Функциональные требования

### 7.1 Пользователи

- Регистрация по e-mail, обязательна с первого запуска (без оффлайн-гостя).
- Авторизация, восстановление пароля.
- Выход со всех устройств (инвалидация refresh-токенов).

### 7.2 Счета

- Создание, редактирование, архивирование.
- Системные типы: Наличные, Дебетовые карты, Кредитные карты, Счета, Вклады — каждый тип настраивается пользователем.
- Иконки конкретных банков.
- Скрытие счёта из общего баланса без архивации.
- **Учёт лимита кредитной карты** — поле `credit_limit`, доступный остаток = лимит − сумма непогашенных расходов по счёту (см. раздел 12).

### 7.3 Категории

- Доходы и расходы, двухуровневая структура (категория → подкатегория).
- Системные и пользовательские категории.
- Признак «обязательная / необязательная» (используется в бюджете, см. 7.5).
- Системные категории нельзя удалить полностью — только скрыть/архивировать (не ломает историю операций).
- При удалении используемой пользовательской категории операции переносятся в категорию «Прочее».
- Иконки — готовая библиотека векторных иконок в едином стиле.

### 7.4 Операции

- Доход, расход, перевод между счетами.
- Разбиение операции на категории (split).
- Повторяющиеся операции (как часть модуля подписок/регулярных платежей).
- Фото-вложение (без OCR — просто прикрепление изображения).
- Комментарий.
- История изменений (audit trail на уровне операции, отдельная таблица-аудит).
- Целевой флоу — счёт → категория → сумма → сохранение, не более 3 действий (см. UC-03/UC-04) — прямое воплощение принципа «< 10 секунд на операцию».

### 7.5 Бюджет

- Периоды: неделя / месяц / год.
- Единая сущность `Budget`; «обязательность» трат выражается через флаг категории `is_mandatory`, отдельной сущности «смета» не создаётся (закрывает открытый вопрос №7 из Bible v1.1).
- Способ создания, перенос остатка и уведомления о лимите — см. рекомендации в разделе 20, п.9.

### 7.6 Накопительные цели

- Создание цели, отслеживание прогресса (прогресс-бар, без AI-рекомендаций в MVP).
- Реализуются как отдельный счёт, привязанный к цели.
- Пополнение/списание — только через обычные операции (без ручной корректировки цели напрямую).

### 7.7 Долги

- Типы: «мне должны» и «я должен».
- **Учёт процентов и график платежей** — обязательно в MVP (см. решение опросника, раздел 20 п.7).
- Связь со счётом: погашение долга автоматически создаёт операцию расхода/дохода.

### 7.8 Подписки

- Учёт регулярных платежей, связаны с повторяющимися операциями (7.4).
- Уведомление о списании — отложено после MVP.
- Отдельный виджет аналитики по подпискам — не нужен, достаточно общего списка.

### 7.9 Аналитика

- Только круговая диаграмма по категориям расходов/доходов за текущий месяц (период по умолчанию).
- Без графиков трендов и без сравнения периодов в MVP.

### 7.10 Экспорт и резервное копирование

- Экспорт только в PDF.
- Бэкап реализуется как снапшот данных на сервере в рамках той же облачной синхронизации — отдельного механизма периодического полного дампа не создаётся (см. решение опросника, раздел 20 п.5).
- Экспорт данных пользователя никогда не ограничивается (принцип владения данными).

### 7.11 Уведомления

- Только локальные (без сети).
- Напоминание внести операцию — не нужно в MVP.
- Настройка уведомлений пользователем — см. рекомендацию в разделе 20, п.10.

## 9. Нефункциональные требования

- **Offline First** — полная функциональность без интернета.
- **Локальное хранение** — источник истины на устройстве, синхронизация — вторична.

- **Надёжность** — потеря данных недопустима ни при каких обстоятельствах.
- **Безопасность** — см. раздел 15.

## 10. Архитектурные принципы

### 10.1 Offline First как архитектурный контракт

Локальная база данных — источник истины (single source of truth) на устройстве. Синхронизация с облаком — асинхронный процесс поверх локальных данных:

- Любая запись сначала попадает в локальную БД и **сразу** отражается в UI.
- Синхронизация — в фоне, с retry-логикой при отсутствии сети, полностью незаметна для пользователя (без индикатора статуса).
- Конфликты разрешаются по стратегии **last-write-wins** (см. раздел 14).

### 10.2 Модульность

Ядро приложения (счета, категории, операции) architecturally отделено от модулей аналитики, целей, долгов/подписок и будущих модулей (семейный бюджет, OCR, AI) — они подключаются как отдельные слои поверх стабильного ядра данных, не изменяя его схему.

### 10.3 Семья как контейнер данных (сохраняется, несмотря на исключение фичи из MVP)

Даже единоличный пользователь на уровне данных рассматривается как «семья из одного участника» (`family_id` как базовый контейнер для всех сущностей). Это принципиальное решение **сохраняется в схеме данных**, несмотря на то, что сама функция приглашения второго участника исключена из MVP-скоупа (раздел 6) — так фича возвращается в будущем без миграции данных.

### 10.4 История изменений (audit trail)

Операции не должны физически удаляться/перезаписываться в БД без сохранения предыдущего состояния — используется `is_deleted` (soft delete) + таблица `transaction_history` для версионирования.

### 10.5 Soft delete — обязателен для всех сущностей

При Offline First с фоновой автосинхронизацией soft delete (`is_deleted`) обязателен для **всех** пользовательских сущностей — иначе удаление на одном устройстве не разрешится корректно при синхронизации на других устройствах, а audit trail не будет иметь смысла.

## 11. Подтверждённый технологический стек

> Раздел закрывает конфликт между Firebase (Biblia) и собственным backend (Bible, раздел 25) в пользу **собственного backend**. Является обязательным источником для реализации.

**Backend:**
- Язык: **Kotlin**
- Фреймворк: **Ktor**
- База данных: **PostgreSQL 14+**
- SQL-слой: **Exposed** (Kotlin DSL от JetBrains)
- DI: **Koin**
- Аутентификация: **JWT** (access + refresh token, инвалидация через таблицу `refresh_token` — закрывает несогласованность из Biblia про Firebase Auth: раз backend свой, JWT остаётся штатным решением)
- Архитектура: Clean Architecture (domain / usecase / repository / delivery)
- Миграции: **Flyway**

**Mobile:**
- Фреймворк: **Flutter**
- State management: **Riverpod**
- Локальная БД: **Isar** (NoSQL, документная, генерируется из Dart-классов) — закрывает конфликт с Drift (Biblia) в пользу Isar (Bible)
- HTTP-клиент: **Dio**
- Архитектура: Clean Architecture (domain / usecase / repository / data / presentation)
- Мин. версия ОС: Android 8+
- Поддержка планшетов: адаптивный UI (уточнить приоритет отдельно, не блокирует MVP)

**Продуктовые технические решения:**
- Валюта: только `RUB` на MVP, поле `currency` присутствует для будущей мультивалютности без миграции.
- Хранение сумм: целые числа в **копейках** (`BIGINT` на сервере, `Int64` на клиенте). Никогда `REAL`/`double` для денег.
- Конфликты синхронизации: last-write-wins по `updated_at`, проигравшая версия сохраняется в `transaction_history`.
- OCR: окончательно исключён из MVP.
- ID записей: **UUID**, генерируются на клиенте (обязательное условие offline-first).

## 12. Модель данных

Состав сущностей: `Family`, `AppUser`, `FamilyMember`, `Account`, `Category`, `Transaction`, `TransactionHistory`, `Budget`, `Goal`, `Debt`, `DebtPayment` *(новое — график платежей)*, `Subscription`.

Общие правила:
- Все ID — UUID.
- Все временные метки — `TIMESTAMPTZ` на сервере, `DateTime` (UTC) на клиенте.
- Все денежные суммы — `BIGINT` в копейках.
- Все сущности привязаны к `family_id` (см. принцип 10.3).
- `is_deleted` (soft delete) применяется ко всем пользовательским сущностям.
- Валютное поле `currency` присутствует, но на MVP всегда `'RUB'`.

**Изменения относительно Bible v1.1** (по итогам опросника):
- `Account` — добавлено поле `credit_limit` (nullable, BIGINT в копейках) для счетов типа «Кредитная карта».
- `Debt` — добавлено поле `interest_rate` (NUMERIC, годовая ставка в %), и новая сущность `DebtPayment` (график платежей: `id`, `debt_id`, `due_date`, `planned_amount`, `is_paid`, `paid_at`).
- `Family`/`FamilyMember` — таблицы сохраняются в схеме (принцип 10.3), но UI приглашения участников и совместного доступа **не реализуется в MVP**.

## 13. Схема БД — DDL

Актуальная серверная схема, PostgreSQL 14+. Дополняет DDL из Bible v1.1 (раздел 25.4) полями для процентов по долгам и лимита кредитки.

```sql
CREATE EXTENSION IF NOT EXISTS "pgcrypto";  -- gen_random_uuid()

CREATE TABLE app_user (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email         TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,               -- argon2id
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE family (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name       TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE TABLE family_member (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    family_id  UUID NOT NULL REFERENCES family(id),
    user_id    UUID NOT NULL REFERENCES app_user(id),
    role       TEXT NOT NULL CHECK (role IN ('OWNER', 'MEMBER')),
    joined_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_deleted BOOLEAN NOT NULL DEFAULT FALSE,
    UNIQUE (family_id, user_id)
);
-- MVP: всегда ровно одна запись family_member с role='OWNER' на семью (family-of-1).
-- Инвайты второго участника — не реализуются до пост-MVP этапа (см. раздел 21).

CREATE TABLE account (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    family_id       UUID NOT NULL REFERENCES family(id),
    name            TEXT NOT NULL,
    type            TEXT NOT NULL,               -- Наличные/Дебетовая/Кредитная/Счёт/Вклад
    currency        TEXT NOT NULL DEFAULT 'RUB',
    initial_balance BIGINT NOT NULL DEFAULT 0,    -- копейки
    credit_limit    BIGINT,                       -- копейки, NULL для не-кредитных счетов
    icon            TEXT,                         -- значок банка
    is_hidden       BOOLEAN NOT NULL DEFAULT FALSE,-- скрыт из общего баланса
    is_archived     BOOLEAN NOT NULL DEFAULT FALSE,
    is_deleted      BOOLEAN NOT NULL DEFAULT FALSE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_account_family ON account(family_id) WHERE is_deleted = FALSE;

CREATE TABLE category (
    id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    family_id          UUID NOT NULL REFERENCES family(id),
    parent_category_id UUID REFERENCES category(id),
    name               TEXT NOT NULL,
    type               TEXT NOT NULL CHECK (type IN ('INCOME', 'EXPENSE')),
    is_mandatory       BOOLEAN NOT NULL DEFAULT FALSE,
    is_system          BOOLEAN NOT NULL DEFAULT FALSE,
    icon               TEXT,
    color              TEXT,
    is_archived        BOOLEAN NOT NULL DEFAULT FALSE,
    is_deleted         BOOLEAN NOT NULL DEFAULT FALSE,
    created_at         TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_category_family ON category(family_id) WHERE is_deleted = FALSE;

CREATE TABLE transaction (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    family_id             UUID NOT NULL REFERENCES family(id),
    account_id            UUID NOT NULL REFERENCES account(id),
    category_id           UUID REFERENCES category(id),
    type                  TEXT NOT NULL CHECK (type IN ('INCOME', 'EXPENSE', 'TRANSFER')),
    target_account_id     UUID REFERENCES account(id),
    amount                BIGINT NOT NULL,              -- копейки
    currency              TEXT NOT NULL DEFAULT 'RUB',
    occurred_at           TIMESTAMPTZ NOT NULL,
    comment               TEXT,
    attachment_photo_path TEXT,
    created_by            UUID NOT NULL REFERENCES app_user(id),
    created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    is_deleted            BOOLEAN NOT NULL DEFAULT FALSE
);
CREATE INDEX idx_transaction_family_date ON transaction(family_id, occurred_at DESC) WHERE is_deleted = FALSE;
CREATE INDEX idx_transaction_account ON transaction(account_id) WHERE is_deleted = FALSE;

CREATE TABLE transaction_history (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    transaction_id UUID NOT NULL REFERENCES transaction(id),
    snapshot_json  JSONB NOT NULL,
    changed_by     UUID NOT NULL REFERENCES app_user(id),
    changed_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_transaction_history_tx ON transaction_history(transaction_id, changed_at DESC);

CREATE TABLE budget (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    family_id      UUID NOT NULL REFERENCES family(id),
    period_type    TEXT NOT NULL CHECK (period_type IN ('WEEK', 'MONTH', 'YEAR')),
    period_start   TIMESTAMPTZ NOT NULL,
    category_id    UUID NOT NULL REFERENCES category(id),
    planned_amount BIGINT NOT NULL,                    -- копейки
    is_deleted     BOOLEAN NOT NULL DEFAULT FALSE,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_budget_family_period ON budget(family_id, period_type, period_start) WHERE is_deleted = FALSE;

CREATE TABLE goal (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    family_id      UUID NOT NULL REFERENCES family(id),
    name           TEXT NOT NULL,
    target_amount  BIGINT NOT NULL,                    -- копейки
    current_amount BIGINT NOT NULL DEFAULT 0,
    target_date    TIMESTAMPTZ,
    is_deleted     BOOLEAN NOT NULL DEFAULT FALSE,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE debt (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    family_id         UUID NOT NULL REFERENCES family(id),
    counterparty_name TEXT NOT NULL,
    direction         TEXT NOT NULL CHECK (direction IN ('I_OWE', 'OWED_TO_ME')),
    amount            BIGINT NOT NULL,                 -- копейки, основная сумма
    interest_rate     NUMERIC(5,2) NOT NULL DEFAULT 0, -- годовая ставка, %
    due_date          TIMESTAMPTZ,
    status            TEXT NOT NULL CHECK (status IN ('OPEN', 'CLOSED')) DEFAULT 'OPEN',
    is_deleted        BOOLEAN NOT NULL DEFAULT FALSE,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Новое: график платежей по долгу (закрывает требование Biblia)
CREATE TABLE debt_payment (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    debt_id        UUID NOT NULL REFERENCES debt(id),
    due_date       TIMESTAMPTZ NOT NULL,
    planned_amount BIGINT NOT NULL,                    -- копейки
    is_paid        BOOLEAN NOT NULL DEFAULT FALSE,
    paid_at        TIMESTAMPTZ,
    transaction_id UUID REFERENCES transaction(id),     -- операция, созданная при погашении
    is_deleted     BOOLEAN NOT NULL DEFAULT FALSE,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_debt_payment_debt ON debt_payment(debt_id) WHERE is_deleted = FALSE;

CREATE TABLE subscription (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    family_id        UUID NOT NULL REFERENCES family(id),
    name             TEXT NOT NULL,
    amount           BIGINT NOT NULL,                  -- копейки
    billing_period   TEXT NOT NULL,
    next_charge_date TIMESTAMPTZ NOT NULL,
    category_id      UUID REFERENCES category(id),
    is_deleted       BOOLEAN NOT NULL DEFAULT FALSE,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Инвалидация JWT-сессий ("выход со всех устройств")
CREATE TABLE refresh_token (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id    UUID NOT NULL REFERENCES app_user(id),
    token_hash TEXT NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    revoked_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_refresh_token_user ON refresh_token(user_id);
```

**Клиентская схема (Isar):** аналогичный набор коллекций (`AccountEntity`, `CategoryEntity`, `TransactionEntity`, `BudgetEntity`, `GoalEntity`, `DebtEntity`, `DebtPaymentEntity`, `SubscriptionEntity`, `TransactionHistoryEntity`), с полями `id` (строковый UUID, совпадает с сервером), служебными `localVersion`, `isDirty`, `lastSyncedAt` для синхронизации. Полный набор классов формализуется на Этапе 0.

## 14. Синхронизация и Offline First

- Способ: автоматически в фоне, без действий пользователя, статус синхронизации **не отображается** в UI.
- Модель: batch pull-push. Клиент периодически (и по событию) вызывает `POST /sync/push` со всеми «грязными» записями, затем `GET /sync/pull?since=<last_synced_at>`.
- ID генерируется на клиенте (UUID) → create и update — одна операция upsert.
- **Конфликты:** last-write-wins по `updated_at`; проигравшая версия сохраняется в `transaction_history` (или аналог для других сущностей).
- **Бэкап** = снапшот данных на сервере в рамках этой же синхронизации; отдельного механизма периодического полного дампа на MVP не создаётся, автоматический бэкап по расписанию не требуется отдельно от sync.

**Черновой контракт эндпоинтов:**

```
POST /auth/register              { email, password }              → { userId, familyId }
POST /auth/login                 { email, password }              → { accessToken, refreshToken }
POST /auth/refresh                { refreshToken }                 → { accessToken, refreshToken }
POST /auth/logout-all             (JWT)                            → 204

GET  /sync/pull?since=<ISO>      (JWT)                            → { entities: {...}, serverTime }
POST /sync/push                   (JWT) { entities: {...} }        → { conflicts: [...], accepted: [...] }
```

## 15. Безопасность и приватность

Явные требования:

- Администратор системы **не имеет доступа** к пользовательским финансам — архитектурное требование.
- Пользователь владеет своими данными — экспорт не может быть ограничен ни функционально, ни коммерчески.
- Хранение платёжных данных — не актуально (приложение полностью бесплатное).

**Закрытые по итогам опросника вопросы [РЕКОМЕНДАЦИЯ]:**

| Вопрос | Рекомендация |
|---|---|
| Способы входа | Только e-mail + пароль на MVP, без соцсетей/OAuth — минимизирует объём работы над своим Auth-сервером |
| Шифрование локальной БД | Isar-БД шифруется at-rest, ключ хранится в Android Keystore (через `flutter_secure_storage`), не передаётся на сервер в открытом виде |
| Биометрическая блокировка | Опциональный тумблер в настройках (`local_auth`), выключен по умолчанию — не блокирует MVP, но реализуется как быстрая фича безопасности |
| Хранение сессии | JWT (access) + refresh-токен, инвалидация через `refresh_token` (раздел 13) |
| Пароли на backend | argon2id, никогда в открытом виде |
| Канал синхронизации | TLS как обязательный минимум |

## 16. Definition of Done

Для **пользовательской истории**:

1. Реализован UI.
2. Реализована бизнес-логика.
3. Реализовано локальное хранение.
4. Реализована синхронизация.
5. Проведено тестирование.

Ни один из пяти пунктов не может быть пропущен.

Для **фичи/экрана** дополнительно — контрольный вопрос: *«Можно ли сделать это быстрее?»* Если да — фича не считается завершённой, пока не переработана.

Для **любого архитектурного решения** — проверка по 4 вопросам из раздела 4.

## 22. Глоссарий

| Термин | Значение |
|---|---|
| Offline First | Принцип, при котором приложение полностью функционирует без интернета; сеть используется только для синхронизации и облачных функций |

## 23. Оставшиеся открытые вопросы

Все пункты ниже закрыты рекомендациями [РЕКОМЕНДАЦИЯ] в соответствующих разделах документа (15, 17, 19) и требуют финального явного подтверждения перед стартом связанного этапа, но не блокируют начало Этапа 0:

1. Способы входа — email+password (раздел 15).
2. Шифрование локальной БД — Isar at-rest + Android Keystore (раздел 15).
3. Биометрическая блокировка — опциональный тумблер (раздел 15).
4. Способ создания бюджета / перенос остатка / уведомления о лимите — единая сущность `Budget`, ручное создание по категориям, без автопереноса остатка на MVP, уведомление при достижении 80%/100% лимита (раздел 7.5).
5. Настройка уведомлений пользователем — тумблеры по категориям уведомлений в настройках (раздел 7.11).
6. Тестовое покрытие финансовой логики — минимум 80% domain/usecase-слоя (раздел 19).
7. Канал поддержки пользователей — e-mail + FAQ (раздел 19).
8. Учёт лимита кредитной карты — поле `credit_limit`, реализация формулы доступного остатка (раздел 7.2, 13).
9. Детализация подписок (уведомления, отмена/изменение цены) — остаётся открытым до Этапа 5.
10. Адаптивный UI под планшеты — заявлен как цель, приоритет уточнить отдельно, не блокирует MVP по Android-телефонам.
