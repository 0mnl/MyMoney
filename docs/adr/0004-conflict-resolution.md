# ADR-0004: Стратегия разрешения конфликтов синхронизации

## Статус
Принято (2026-07-18)

## Контекст

MyMoney работает в модели Offline First (§ 10.1 Bible): локальная БД на устройстве — источник истины, сервер — точка сведения. Семейный бюджет допускает двух участников (§ 6.7), каждый из которых может редактировать одни и те же сущности (счета, операции, категории, бюджет, цели, долги, подписки) на своих устройствах офлайн. При восстановлении сети возможны конфликты — две версии одной и той же записи с разными полями.

Bible § 10.1 и § 22 обозначили проблему, но конкретная стратегия оставалась открытым вопросом № 4 (§ 18). Требование, зафиксированное в § 9: **потеря данных недопустима ни при каких обстоятельствах**, включая конфликты синхронизации.

Альтернативные стратегии:
1. **Last-write-wins (LWW)** по `updated_at` — принять более свежую запись, отбросить старую.
2. **Field-level merge** — сливать по полям (например, комментарий одного пользователя + сумма другого).
3. **Multi-version** — хранить обе версии, требовать ручного разрешения пользователем.
4. **CRDT (например, Automerge)** — автоматическое слияние на уровне структур.

## Решение

**Last-write-wins по `updated_at` — с обязательным сохранением проигравшей версии в `transaction_history` (или аналогичной таблице истории для других сущностей).**

Правила:
1. Каждая пользовательская запись имеет `updated_at` (`TIMESTAMPTZ` на сервере, `DateTime` UTC на клиенте) — время последнего локального изменения.
2. При sync-push сервер сравнивает `updated_at` клиентской версии с серверной. Побеждает более свежая.
3. **Если побеждает клиентская версия** — сервер обновляет запись, возвращает `accepted`.
4. **Если побеждает серверная версия** — сервер возвращает конфликт (`conflicts` в ответе push), клиент **обязан**:
   - Сохранить проигравшую локальную версию в таблицу истории (`transaction_history` для операций; для остальных сущностей аналогичный механизм добавляется по мере необходимости).
   - Принять серверную версию как актуальную.
5. Часы сервера считаются авторитетными для разрешения "ничьих" (одинаковый `updated_at` — побеждает сервер). Клиент не должен полагаться на строгую монотонность своих часов; для внутренней монотонности локальных изменений использовать `local_version` (см. Bible § 25.5).

Тонкости реализации:
- `updated_at` устанавливается на клиенте в момент любой локальной модификации, **до** записи в локальную БД.
- Часовые пояса — всегда UTC на транспорте и в БД. Локализация — только на слое presentation.
- При soft-delete (`is_deleted = true`) правило LWW применяется тем же способом — удаление проигрывает более позднему изменению и наоборот.

## Обоснование

- **Простота реализации критична для MVP.** Полнофункциональный field-level merge или CRDT удлиняют цикл разработки в разы. LWW реализуется за несколько десятков строк кода и покрывается тестами линейно.
- **История сохраняется в любом случае.** Проигравшая версия не теряется, а становится записью в audit trail — пользователь может её увидеть и восстановить вручную. Это удовлетворяет требование "потеря данных недопустима" на уровне продукта.
- **Реальные конфликты редки в семье из 2 человек.** MVP-скоуп ограничен 2 участниками (§ 6.7). Пик "одновременной правки одной записи" в этом сценарии — маргинален; в 99% случаев конфликтов не будет вовсе.
- **Field-level merge — рискованное решение.** Слить комментарий одного пользователя с суммой другого — потенциально ввести пользователя в заблуждение о том, что операция подтверждена.
- **CRDT — избыточная сложность.** Требует переработать модель данных, добавить операционные логи для каждой сущности, поддерживать структурные типы. Не оправдано для скоупа MVP.

## Последствия

**Правила, вступающие в силу:**
- Все пользовательские сущности имеют поля `updated_at` и `is_deleted` — не может быть исключений (§ 25.2 Bible).
- Клиентская логика sync-push обязана обрабатывать поле `conflicts` в ответе. Отсутствие обработки — критический баг.
- Таблица `transaction_history` — не опция, а обязательная часть системы. Аналогичные таблицы для других сущностей добавляются по мере необходимости (в первую очередь для `budget` — планы бюджета редактируются часто).
- Часы устройства должны быть в разумных пределах точности (не отставать на дни). При обнаружении сильного расхождения между клиентскими и серверными часами — предупреждать пользователя. Отдельная проверка на клиенте: `abs(now() - server_time) < N минут`.

**Тесты, обязательные для Этапа 4 (см. § 24 Bible):**
- Конкурентная правка одной операции с двух устройств → проигравшая версия в `transaction_history`, обе версии восстановимы.
- Soft-delete на устройстве A и правка на устройстве B — проверить оба порядка (кто быстрее — побеждает).
- Клиент с сильно отстающими часами (>1 день) — предупреждение / отказ синхронизации.
- Одновременная правка с идентичным `updated_at` — детерминированное поведение (побеждает сервер).

**Что делать при обнаружении неудобства LWW на практике:**
- Собирать данные о частоте конфликтов через телеметрию (в пост-MVP).
- Если field-level merge окажется востребован — реализовать выборочно для наиболее часто редактируемых полей (например, `comment` у операции).
