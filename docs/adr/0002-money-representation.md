# ADR-0002: Представление денежных сумм

## Статус
Принято (2026-07-18)

## Контекст

MyMoney работает с финансовыми суммами — операциями, остатками, планами бюджета, целями, долгами, подписками. Любая ошибка округления недопустима: пользователь ожидает, что сумма его операций совпадёт до копейки с балансом счёта (см. § 2 Bible: "Потеря пользовательских данных — критическая ошибка"). Одновременно на MVP валюта фиксирована — только российский рубль (закрытие открытого вопроса № 6 Bible).

Черновая схема в § 21 Bible использовала `REAL` (SQLite floating-point) для сумм, что несовместимо с этим требованием: `REAL` не является точным типом, накопление операций даёт ошибки округления вида `0.1 + 0.2 != 0.3`.

## Решение

1. Все денежные суммы хранятся как **целые числа в минимальной единице валюты — копейках**.
2. На сервере (PostgreSQL) используется тип `BIGINT`.
3. На клиенте (Dart/Flutter) используется `int` (64-битный на всех целевых платформах).
4. Форматирование в рубли и копейки (`123 456,78 ₽`) выполняется **только на слое presentation** (Dart — `intl` пакет, серверные логи — helper-функция).
5. Валютное поле `currency TEXT NOT NULL DEFAULT 'RUB'` физически присутствует во всех денежных таблицах/коллекциях. На MVP значение всегда `'RUB'`. Это позволит добавить мультивалютность в пост-MVP без миграции схемы.
6. Операции конвертации между валютами **не реализуются** на MVP — все суммы в одной валюте, конвертация не требуется.

## Обоснование

- **Целые числа исключают ошибки округления.** Стандартная практика финансовых систем — хранить и вычислять в минимальных единицах, форматировать только на выходе.
- **`BIGINT` (8 байт, ±9,2 × 10¹⁸) с запасом.** Даже суммарный ВВП России в копейках помещается многократно. Ограничения размера не будет достигнуто в разумных сценариях.
- **Dart `int` 64-битный на мобильных.** Web-target (Dart-to-JS) имеет ограничение 53 бита, но web не входит в MVP. Если приложение будет портировано на web — придётся использовать `BigInt` или строковое представление; отложено до пост-MVP.
- **Отсутствие `Decimal` в Postgres выглядит альтернативой**, но `BIGINT` быстрее и не имеет ловушек масштаба; `NUMERIC(20,2)` избыточен, пока валюта одна.
- **Поле `currency` без активной мультивалютности** — минимальный overhead (несколько байт на строку), но огромная экономия при будущей миграции: не нужно `ALTER TABLE` для добавления колонки, все запросы уже включают валюту в фильтр.

## Последствия

**Правила, вступающие в силу:**
- Любое поле `amount`, `planned_amount`, `target_amount`, `current_amount`, `initial_balance`, `next_charge_date`.amount — `BIGINT` на сервере и `int` в Isar. Never `REAL` / `double`.
- Любой ввод от пользователя (`123,45`) на клиенте немедленно конвертируется в копейки (`12345`) перед сохранением. Никакой `double` не покидает слой parsing.
- Тесты денежных вычислений обязательны для каждого use case, работающего с суммой. Хотя бы один тест на копеечную границу (например, `12345 копеек / 3` должно давать корректный round).
- Валютные операции (сумма разных валют, конвертация) физически невозможны на MVP — при попытке компиляция должна падать (валидация на domain-слое).

**Что делать при добавлении мультивалютности (пост-MVP):**
- Валюта уже есть в схеме — не требуется миграция таблиц.
- Потребуется: сервис курсов валют, стратегия хранения курса на момент транзакции, UI выбора валюты счёта, отчёты в базовой валюте.
- Отдельным ADR закрепить: конвертация происходит по курсу на дату операции, а не в момент отображения (для консистентности отчётов).
