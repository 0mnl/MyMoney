# ADR-0001: Выбор технологического стека

## Статус
Принято (2026-07-18)

## Контекст

MyMoney — коммерческое приложение для управления личными и семейными финансами с расчётом на многолетнее развитие без переписывания ядра (см. § 1 Bible). MVP разрабатывается для Android с прицелом на iOS в будущем. Ключевые архитектурные требования, влияющие на выбор стека:

- **Offline First** — локальная БД является источником истины на устройстве (§ 10.1).
- **Отделение бизнес-логики от UI** для возможности переиспользования между платформами.
- **Долгосрочная поддержка** — язык/фреймворк должны быть живы и активно развиваться через 3–5 лет.
- **Администратор системы не имеет доступа к финансовым данным пользователей** (§ 13) — требуется контроль над серверной логикой.

Черновой раздел § 11 Bible предлагал Kotlin Multiplatform + Compose как основной вариант. Пользователь отверг KMP и выбрал разделённый стек: Kotlin для сервера, Flutter для клиента.

## Решение

### Backend

- **Язык:** Kotlin
- **Фреймворк:** Ktor
- **База данных:** PostgreSQL 14+
- **SQL-слой:** Exposed (обоснование — ADR-0003)
- **DI:** Koin
- **Аутентификация:** JWT (access + refresh tokens, серверная инвалидация через таблицу `refresh_token`)
- **Миграции:** Flyway
- **Архитектура:** Clean Architecture (`domain` / `usecase` / `repository` / `delivery`)

### Mobile

- **Фреймворк:** Flutter (стабильная ветка)
- **State management:** Riverpod
- **Локальная БД:** Isar (NoSQL, документная)
- **HTTP-клиент:** Dio
- **Архитектура:** Clean Architecture (`domain` / `usecase` / `repository` / `data` / `presentation`)

## Обоснование

**Почему Ktor на бэке.** Полный контроль над схемой синхронизации и шифрования — Firebase/Supabase не дают достаточно тонкой настройки под требование "администратор не имеет доступа к финансам". Kotlin — зрелая экосистема, хорошая интеграция с JVM, живая поддержка от JetBrains. Ktor легковеснее Spring, идеологически ближе к минимализму и подходит для API-first приложения без монолитной админки.

**Почему Flutter, а не нативный Android/KMP.** При равном приоритете iOS в горизонте нескольких лет Flutter даёт максимальную переиспользуемость UI-слоя без прослойки в Dart-логике. Isar — одна из самых быстрых локальных БД в экосистеме Flutter, документная модель хорошо ложится на offline-first сценарий с последующей синхронизацией через REST. Riverpod — современный, компилируемый, безопасный по типам, актуальный на 2025–2026 гг.

**Почему разделение языков (Kotlin + Dart), а не единый KMP.** Пользователь оценил гибкость и скорость разработки на Flutter выше архитектурной гомогенности KMP. Разделение приемлемо, потому что бизнес-логика клиента и сервера всё равно решает разные задачи: клиент — offline-first UI и локальный кэш, сервер — сведение состояния и авторизация.

## Последствия

**Плюсы:**
- Независимая эволюция клиента и сервера, разные release cycle.
- Богатая экосистема Flutter для UI-задач (графики, PDF, аналитика).
- Стандартный REST-контракт вместо специализированного KMP-моста упрощает добавление web/desktop клиентов в будущем.

**Минусы / компромиссы:**
- Модели данных дублируются в Kotlin (`domain/model`) и Dart (`domain/model`) — требуется дисциплина по синхронизации схем. Митигация: OpenAPI-спека в `docs/api/` как источник истины для DTO.
- Бизнес-правила (например, расчёт баланса, разрешение конфликтов синхронизации) реализуются дважды. Митигация: покрытие обеих реализаций одним набором тест-кейсов из спецификации.

**Что должно быть сделано следующим шагом:**
- ADR-0002 (представление денег), ADR-0003 (Exposed), ADR-0004 (стратегия конфликтов), ADR-0005 (REST-контракт синхронизации).
- Раздел § 25.3 Bible — принятая структура репозитория.
