# ADR-0003: SQL-слой на бэкенде — Exposed

## Статус
Принято (2026-07-18)

## Контекст

Бэкенд MyMoney написан на Kotlin + Ktor + PostgreSQL (см. ADR-0001). Требуется выбрать способ работы с БД:

- **jOOQ** — типобезопасный SQL DSL, генерация кода из существующей схемы. Индустриальный стандарт для критичных к производительности сервисов.
- **Exposed** — Kotlin DSL от JetBrains, два стиля (DSL + DAO), не требует code-generation.
- **JDBI 3** — тонкая обёртка над JDBC с шаблонизацией SQL.
- **Ktorm** — альтернативный Kotlin ORM.
- **Голый JDBC / pgx-style** — максимальный контроль, минимум магии.

Требования проекта, влияющие на выбор:
- Clean Architecture: SQL-слой изолирован в `data/db`, `data/repository`. UI/domain никогда не видят SQL.
- Миграции — через Flyway (SQL-файлы), а не через ORM. Схема — источник истины (§ 25.4 Bible).
- Долгосрочная поддержка (§ 1 Bible).
- Скоуп сравнительно небольшой: около 10 таблиц (§ 25.4), в основном простые CRUD-запросы + несколько агрегаций для аналитики.

## Решение

Использовать **Exposed** (актуальная стабильная версия) в стиле **DSL** (не DAO).

- Таблицы описываются как Kotlin-объекты в `backend/src/main/kotlin/mymoney/data/db/tables/`.
- Запросы пишутся через `Exposed DSL` внутри реализаций репозиториев (`data/repository`).
- Миграции — только через Flyway (`src/main/resources/db/migration/`). Exposed **не** используется для генерации/изменения схемы (`SchemaUtils.create()` запрещён в production-коде).
- DAO-стиль (Entity-классы Exposed) **не используется** — все репозитории возвращают доменные модели (`domain/model`), не Exposed-entity.
- Подключение к БД настраивается через HikariCP.

## Обоснование

**Почему Exposed, а не jOOQ.**
- Скоуп MVP не требует уровня контроля jOOQ. Около 10 таблиц, преимущественно CRUD, лёгкие агрегации — Exposed справляется без потери читаемости.
- Отсутствие code-generation ускоряет цикл разработки: миграция → сразу правка Kotlin-таблиц без промежуточного шага.
- Официальная поддержка JetBrains — согласовано с политикой "долгосрочная поддержка" (Kotlin + JetBrains инструменты).
- jOOQ платный для Postgres в enterprise-редакции; open-source-редакция достаточна, но её экосистема сложнее.

**Почему Exposed DSL, а не DAO.**
- Clean Architecture требует чистого domain-слоя без утечки инфраструктурных типов. Exposed-DAO Entity мешают этому: их сложно передать наружу без превращения в утечку абстракции.
- DSL легче тестировать: репозиторий возвращает pojo/data class, тестируется чистая функция маппинга.

**Почему миграции — только Flyway, не Exposed `SchemaUtils`.**
- `SchemaUtils.create()` не поддерживает миграций (только добавление недостающих объектов). Для production он опасен и приводит к дрейфу схемы.
- SQL-миграции — стандарт индустрии, легко читаются, легко ревьюятся, безопасно применяются в CI/CD.

## Последствия

**Правила, вступающие в силу:**
- В `data/db/tables/` лежат `Exposed.Table` объекты, описывающие структуру, но **не** источник истины схемы. Источник истины — SQL-файлы миграций.
- Если Exposed-описание расходится с миграцией — ошибка в Exposed-таблице (миграция всегда права).
- Репозитории (`data/repository/*Impl.kt`) содержат Exposed DSL внутри `transaction { ... }` блоков, но возвращают только доменные модели.
- Никаких `SchemaUtils.create()` / `SchemaUtils.createMissingTablesAndColumns()` в production-коде. Разрешены только в интеграционных тестах, где схема поднимается через миграцию.
- Тесты репозиториев работают на Testcontainers Postgres (не in-memory H2 — риск диалектных различий).

**Что делать при росте сложности запросов:**
- Аналитические агрегации (§ 6.10 Bible) — если Exposed DSL становится нечитаемым, разрешено использовать raw SQL через `Query.execAndMap { ... }`.
- При переходе за ~50 таблиц или сложные CTE — переоценить решение отдельным ADR (замена на jOOQ).

## Альтернативы, отвергнутые

- **jOOQ:** избыточен для скоупа MVP, дополнительный шаг генерации.
- **JDBI:** отсутствие типобезопасного DSL — придётся писать сырые SQL-строки, ручной маппинг → больше ошибок.
- **Ktorm:** менее популярен, риск угасания поддержки.
- **Голый JDBC:** слишком много boilerplate, снижает читаемость.
