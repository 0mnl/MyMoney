## 1. Миссия и видение

### Проект

MyMoney — современная система управления личными и семейными финансами, ориентированная на максимально простой ежедневный учет денежных средств, долгосрочное финансовое планирование и развитие финансовой дисциплины пользователя.

Проект создаётся как коммерческий программный продукт для публикации в Google Play и Apple App Store, с расчётом на поддержку в течение многих лет. Архитектура должна предполагать постоянное развитие **без необходимости полного переписывания** существующего кода.

### Миссия

Создать простое, быстрое и надёжное приложение для ведения личного и семейного бюджета, которым удобно пользоваться ежедневно без специальных финансовых знаний.

### Видение (горизонт нескольких лет)

MyMoney должен стать экосистемой управления личными финансами, включающей:

- Android и iOS приложения;
- безопасную облачную синхронизацию;
- совместный семейный бюджет;
- накопительные цели;
- резервное копирование;
- интеллектуальную аналитику (будущие версии);
- OCR и AI-помощника (будущие версии).

### Главная идея

Большинство приложений учёта бюджета заставляют пользователя постоянно думать о самом приложении. MyMoney должен делать обратное — пользователь думает только о своих финансах, а не о том, как ими управлять в приложении.

**Основная цель проекта** — максимально уменьшить количество действий пользователя при сохранении высокой точности учёта финансов.

## 2. Философия продукта

### Чем MyMoney не является

- Не бухгалтерская система.
- Не система управления предприятием.
- Не банковское приложение.

MyMoney — **персональный финансовый помощник**.

### Ценности продукта

1. Пользователь всегда владеет своими данными.
2. Offline First — отсутствие интернета не должно блокировать работу.
3. Минимум действий для выполнения любой задачи.
4. Архитектура важнее быстрых временных решений.
5. Безопасность и надёжность — обязательные требования, а не опции.

### Приоритеты проекта

Простота → Скорость → Надёжность → Безопасность → Понятность.

### Что никогда не должно происходить

- Запрещено принимать решения, ухудшающие пользовательский опыт ради уменьшения количества кода.
- Красивый код никогда не важнее удобства пользователя.

### Ключевые принципы

| Принцип | Формулировка |
|---|---|
| Простота | Любое действие требует минимального количества нажатий |
| Скорость | Добавление новой операции — менее 10 секунд |
| Надёжность | Потеря пользовательских данных — критическая ошибка |
| Offline First | Приложение полностью функционирует без интернета |
| Владение данными | Экспорт данных никогда не ограничивается |

Интернет используется **только** для: синхронизации, резервного копирования, регистрации, семейного бюджета, облачных функций. Всё остальное работает локально.

### Правило "можно ли быстрее"

При проектировании любого нового экрана задаётся вопрос:

> Можно ли сделать это быстрее?

Если ответ «да» — интерфейс перерабатывается. Это правило применяется на каждом ревью UI/UX перед принятием фичи в разработку.

## 3. Целевая аудитория

- Пользователи 18–45 лет.
- Люди, ведущие личный бюджет.
- Семьи из двух человек (на этапе MVP семейный бюджет ограничен 2 участниками).
- Пользователи без бухгалтерского образования — интерфейс и терминология должны быть понятны без специальных знаний.

---

## 4. Принцип принятия решений

Это центральный механизм разрешения споров при разработке — любое архитектурное или продуктовое решение должно проверяться по следующей логике, **в порядке приоритета**:

1. **Быстрое решение vs правильная архитектура** → выбирается **архитектура**.
2. **Архитектура vs удобство пользователя** → выбирается **удобство пользователя**.

Дополнительно, для каждого решения нужно ответить на 4 вопроса:

1. Улучшает ли оно пользовательский опыт?
2. Соответствует ли Offline First?
3. Не нарушает ли архитектуру?
4. Позволяет ли масштабировать проект в будущем?

Если хотя бы один ответ отрицательный — решение пересматривается.

Финальная проверочная формула для любого решения:

> Поможет ли это сделать приложение проще, быстрее, надёжнее и удобнее через три года?

## 5. Границы MVP

### Входит в MVP

- Регистрация и авторизация (по e-mail)
- Локальное хранение данных
- Облачная синхронизация
- Счета
- Категории
- Доходы и расходы
- Планирование бюджета
- Накопительные цели
- Семейный бюджет (до 2 участников)
- Долги
- Подписки
- Круговая аналитика
- Резервное копирование

### Не входит в MVP

- Инвестиции
- Криптовалюты
- Акции
- Банковские API
- OCR
- AI
- Голосовой ввод
- Геолокация
- Web-версия
- Telegram-бот
- Импорт данных
- Расширенная аналитика

> ⚠️ **Важно:** сканирование и распознавание чеков (OCR) сознательно исключено из MVP во всех исходных документах. Это выглядит как осознанное сужение скоупа относительно изначальной идеи проекта (см. раздел 18 — открытые вопросы).

### Платформы

MVP разрабатывается для **Android**. iOS — часть долгосрочного видения, но не MVP. Архитектурные решения (см. раздел 11) должны быть выбраны так, чтобы переход на iOS не требовал переписывания бизнес-логики.

## 6. Функциональные требования

### 6.1 Пользователи

- Регистрация по e-mail.
- Авторизация.
- Выход со всех устройств.
- Восстановление пароля.

### 6.2 Счета

- Создание, редактирование, архивирование.
- Пользовательские типы счетов.
- Баланс счёта.

### 6.3 Категории

- Доходы и расходы.
- Двухуровневая структура (категория → подкатегория).
- Системные (предустановленные) и пользовательские категории.
- Признак «обязательная / необязательная».
- Системные категории редактируемы пользователем, но не удаляемы полностью (см. раздел 18 — открытые вопросы по поведению при удалении/скрытии).

### 6.4 Операции

- Доход.
- Расход.
- Перевод между счетами.
- Фото-вложение (без OCR — просто прикрепление изображения к операции).
- Комментарий.
- История изменений (audit trail на уровне операции).

### 6.5 Бюджет (смета)

- Недельный.
- Месячный.
- Годовой.

### 6.6 Накопительные цели

- Создание цели.
- Отслеживание прогресса.
- Рекомендации по накоплению (правило-ориентированные, без AI).

### 6.7 Семья

- До 2 участников.
- Приглашение участника.
- Общие данные (счета/категории/операции в рамках семейного бюджета).

### 6.8 Долги

- Учёт долгов (кто кому должен / я должен).
- (Детализация полей — см. раздел 18, открытый вопрос).

### 6.9 Подписки

- Учёт регулярных платежей (подписки, регулярные расходы).
- (Детализация — уведомления, периодичность — см. раздел 18).

### 6.10 Аналитика

- Круговая диаграмма по категориям расходов/доходов.
- Отчёты за неделю, месяц, год (агрегация по периодам).

### 6.11 Экспорт и резервное копирование

- Экспорт в PDF.
- Резервное копирование данных.
- Экспорт данных пользователя никогда не должен ограничиваться (принцип владения данными).

## 7. Пользовательские истории

### Пользователь

Как пользователь, я хочу:

- зарегистрироваться;
- войти с нового устройства;
- добавить доход;
- добавить расход;
- изменить категорию;
- видеть баланс счетов;
- планировать бюджет;
- отслеживать прогресс целей;
- вести совместный бюджет;
- экспортировать PDF;
- создавать резервные копии.

### Администратор системы

- Управляет серверной частью.
- **Не имеет доступа** к пользовательским финансовым данным (принципиальное требование к архитектуре шифрования/доступа на бэкенде).

### Definition of Done для пользовательской истории

Каждая пользовательская история считается завершённой только после реализации:

1. UI;
2. бизнес-логики;
3. локального хранения;
4. синхронизации;
5. тестирования.

Ни один из этих пяти пунктов не может быть пропущен при закрытии истории — иначе история не считается выполненной.

## 9. Нефункциональные требования

- **Offline First** — полная функциональность без интернета.
- **Локальное хранение** — источник истины на устройстве, синхронизация — вторична.
- **Облачная синхронизация** — между устройствами и для семейного бюджета.
- **Высокая производительность** — мгновенный отклик интерфейса, никаких задержек при вводе операций.
- **Масштабируемая архитектура** — возможность добавлять модули (OCR, AI и т.д. из пост-MVP списка) без переписывания ядра.
- **Надёжность** — потеря данных недопустима ни при каких обстоятельствах (сбой сети, конфликт синхронизации, крэш приложения).
- **Безопасность** — см. раздел 13.

## 10. Архитектурные принципы

### 10.1 Offline First как архитектурный контракт

Локальная база данных — это **источник истины** (single source of truth) на устройстве. Синхронизация с облаком — асинхронный процесс поверх локальных данных, а не обязательное условие работы. Практически это означает:

- Любая операция записи сначала попадает в локальную БД и **сразу** отражается в UI.
- Синхронизация с сервером происходит в фоне, с retry-логикой при отсутствии сети.
- Конфликты синхронизации (например, правка одной операции с двух устройств) должны разрешаться по чёткой, заранее определённой стратегии (например, last-write-wins с сохранением истории конфликтов, либо merge на уровне полей) — стратегия требует отдельного решения перед реализацией синхронизации семейного бюджета.

### 10.2 Модульность

Поскольку в манифесте прямо зафиксировано требование "развитие без полного переписывания", ядро приложения (счета, категории, операции) должно быть architecturally отделено от:

- модулей аналитики,
- модуля целей,
- модуля долгов/подписок,
- будущих модулей (OCR, AI) — они должны подключаться как отдельные слои поверх стабильного ядра данных, не изменяя его схему.

### 10.3 Семейный бюджет как расширение, а не как частный случай

Даже единоличный пользователь на уровне данных должен рассматриваться как "семья из одного участника". Это позволяет включить функцию приглашения второго участника без миграции данных пользователя. Такой подход прямо следует из принципа "масштабируемость без переписывания".

### 10.4 История изменений (audit trail)

Требование "история изменений" для операций означает, что операции не должны физически удаляться/перезаписываться в БД без сохранения предыдущего состояния — нужен механизм versioning или event log на уровне транзакций, а не простое обновление записи.

## 11. Технологический стек [РЕКОМЕНДАЦИЯ]

> ⚠️ **ЗАМЕЩЁН разделом 25 (Подтверждённый стек v1.1).** Содержимое ниже сохранено как исторический контекст обсуждения альтернатив (KMP+Compose vs Flutter). Актуальные технологические решения — в разделе 25.

### Мобильное приложение

**Kotlin Multiplatform (KMP) + Jetpack Compose (Android UI)**

Обоснование:
- Общий модуль бизнес-логики, работы с БД и синхронизации на Kotlin — при переходе на iOS переписывается только UI-слой, а не ядро.
- Полный доступ к нативным Android API без прослойки (важно для камеры/фото-вложений, работы в фоне, надёжности хранения).
- Kotlin — единственный официально поддерживаемый Google язык первого класса для Android, что важно для многолетней поддержки.

Альтернатива — Flutter, если приоритет на счёту максимально быстрый запуск на двух платформах одновременно, а не архитектурная чистота разделения слоёв. Учитывая явный принцип манифеста "архитектура важнее быстрого решения", KMP выглядит более согласованным с философией проекта.

### Локальная база данных

**SQLDelight** (или Room, если решено остаться чисто на Android без KMP) — типобезопасные SQL-запросы, хорошая поддержка миграций схемы, что критично при долгосрочном развитии без переписывания.

### Синхронизация и бэкенд

Варианты для обсуждения:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Firebase (Firestore + Auth) | Быстрый старт, готовая авторизация, realtime sync из коробки | Меньше контроля над схемой конфликтов, vendor lock-in |
| Собственный backend (Kotlin/Ktor или Node + PostgreSQL) | Полный контроль над логикой синхронизации, шифрованием, доступом | Больше времени на разработку и поддержку инфраструктуры |
| Supabase | PostgreSQL "из коробки" + realtime + auth, меньше vendor lock-in чем Firebase | Моложе экосистема, меньше готовых решений под мобильные офлайн-сценарии |

Учитывая требование "администратор системы не имеет доступа к финансовым данным пользователя" — при любом варианте потребуется **шифрование данных на уровне клиента** (end-to-end или хотя бы at-rest с ключом, недоступным бэкенду в открытом виде).

### Аналитика и графики

Vico или MPAndroidChart для круговых диаграмм и отчётов — оба зрелые, бесплатные, хорошо работают с Compose.

### Экспорт PDF

## 13. Безопасность и приватность

Явные требования из документов:

- Администратор системы **не имеет доступа** к пользовательским финансам — архитектурное требование, а не просто политика.
- Пользователь владеет своими данными — экспорт не может быть ограничен ни функционально, ни коммерчески (например, платной подпиской).

Вытекающие технические требования **[РЕКОМЕНДАЦИЯ]**:

- Шифрование финансовых данных at-rest на устройстве.
- Шифрование канала синхронизации (TLS) — обязательный минимум.
- Рассмотреть шифрование данных на сервере таким образом, чтобы расшифровка была возможна только на стороне клиента (ключ либо выводится из пароля пользователя, либо хранится в защищённом хранилище устройства — Android Keystore).
- Хэширование паролей на бэкенде (bcrypt/argon2), не хранить в открытом виде нигде.
- Двухфакторная защита при "выходе со всех устройств" — необходим механизм инвалидации сессий/токенов на сервере.

## 18. Открытые вопросы

Эти вопросы не имеют однозначного ответа в исходных документах и требуют решения перед началом или в процессе разработки соответствующих модулей:

1. **OCR чеков.** В твоём первоначальном описании идеи проекта сканирование чеков было ключевой функцией MVP. Во всех пяти документах (Манифест, Vision, PRD) OCR явно исключён из MVP и отнесён к будущим версиям. Нужно подтвердить: это осознанное решение о пересмотре скоупа, актуальное на сейчас?

2. **Долги — детализация.** PRD и user stories не раскрывают поля и сценарии для модуля долгов (проценты? график погашения? уведомления о сроках?). Требуется отдельная проработка перед этапом 5 дорожной карты.

3. **Подписки — детализация.** Аналогично: не описаны уведомления, обработка отмены/изменения цены подписки, привязка к конкретному счёту.

4. **Стратегия разрешения конфликтов синхронизации.** Не определена в документах — критична для семейного бюджета, где два участника могут одновременно редактировать одну операцию.

5. **Поведение системных категорий при "удалении".** PRD говорит "системные и пользовательские категории", но не уточняет, может ли пользователь удалить системную категорию, или только скрыть/архивировать её.

6. **Валюта.** Не упомянута явно ни в одном документе — предполагается ли мультивалютность счетов с самого MVP, или один счёт = одна валюта без конвертации?

7. **Определение "смета" vs "бюджет".** В твоём первом сообщении "смета" — это планирование обязательных расходов. В PRD термин "бюджет" используется шире (недельный/месячный/годовой, без явного разделения на обязательные/необязательные траты). Стоит явно зафиксировать: смета — это подмножество бюджета по обязательным категориям, или отдельная сущность?

### 19.1 Architecture Decision Records (ADR)

Каждое значимое архитектурное решение (выбор стека, стратегия синхронизации, шифрование и т.д.) фиксируется отдельным файлом в `docs/adr/`, по шаблону:

```
docs/adr/0001-choice-of-kmp.md
docs/adr/0002-conflict-resolution-strategy.md
docs/adr/0003-encryption-approach.md
```

Формат ADR (кратко):

```markdown
# ADR-000X: Название решения

## Статус
Предложено / Принято / Отклонено / Заменено ADR-00YY

## Контекст
Какая проблема решается.

## Решение
Что решено.

## Последствия
Что это значит для дальнейшей разработки.
```

Это даёт Claude Code возможность понимать **почему** был сделан тот или иной выбор, не перечитывая всю историю чата — критично, учитывая требование манифеста "развитие без переписывания".

## 20. Конвенции кода и именования [РЕКОМЕНДАЦИЯ]

Единые правила, обязательные для любого кода, который пишется в проекте (человеком или агентом):

- **Язык кода и комментариев:** Kotlin-код, имена классов/функций/переменных — на английском. Комментарии и docstring — на английском, если не решено иначе (единообразие важнее личных предпочтений).
- **Именование пакетов:** `mymoney.<layer>.<module>`, например `mymoney.domain.usecase.transaction`.
- **Use case — один класс = одно действие.** Например `AddTransactionUseCase`, `CalculateMonthlyBudgetUseCase`. Не создавать "толстые" сервисы с десятком методов.
- **Репозитории** объявляются интерфейсом в `domain/repository`, реализуются в `data/repository`. UI и use case'ы никогда не обращаются напрямую к SQLDelight/API — только через интерфейс репозитория. Это защищает принцип модульности (раздел 10.2).
- **Никаких прямых обращений к сети из UI-слоя.** Вся сетевая логика — только через `sync`-модуль.
- **Миграции схемы БД** — всегда через версионированные `.sqm`-файлы (SQLDelight) или Room Migration-классы, никогда не через `fallbackToDestructiveMigration` — потеря данных пользователя недопустима (принцип надёжности, раздел 2).
- **Именование веток git:** `feature/<модуль>-<краткое-описание>`, `fix/<модуль>-<баг>`, например `feature/transactions-history-audit-trail`.
- **Commit-сообщения:** Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`), например `feat(transactions): add photo attachment support`.

## 21. Схема базы данных — DDL [РЕКОМЕНДАЦИЯ]

> ⚠️ **ЗАМЕЩЁН разделом 25.4 (Postgres DDL v1.1) и 25.5 (Isar-схемы v1.1).** Ниже — исходный SQLite-DDL под SQLDelight; актуальные схемы под Postgres (сервер) и Isar (клиент) — в разделе 25. Суммы теперь хранятся как `BIGINT` в копейках, ID — `UUID`, время — `TIMESTAMPTZ`.

```sql
CREATE TABLE family (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    created_at INTEGER NOT NULL
);

CREATE TABLE user (
    id TEXT PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    created_at INTEGER NOT NULL
);

CREATE TABLE family_member (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL REFERENCES family(id),
    user_id TEXT NOT NULL REFERENCES user(id),
    role TEXT NOT NULL CHECK (role IN ('OWNER', 'MEMBER')),
    joined_at INTEGER NOT NULL
);

CREATE TABLE account (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL REFERENCES family(id),
    name TEXT NOT NULL,
    type TEXT NOT NULL,
    currency TEXT NOT NULL,
    initial_balance REAL NOT NULL DEFAULT 0,
    is_archived INTEGER NOT NULL DEFAULT 0,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);

CREATE TABLE category (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL REFERENCES family(id),
    parent_category_id TEXT REFERENCES category(id),
    name TEXT NOT NULL,
    type TEXT NOT NULL CHECK (type IN ('INCOME', 'EXPENSE')),
    is_mandatory INTEGER NOT NULL DEFAULT 0,
    is_system INTEGER NOT NULL DEFAULT 0,
    icon TEXT,
    color TEXT,
    is_archived INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE transactions (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL REFERENCES family(id),
    account_id TEXT NOT NULL REFERENCES account(id),
    category_id TEXT REFERENCES category(id),
    type TEXT NOT NULL CHECK (type IN ('INCOME', 'EXPENSE', 'TRANSFER')),
    target_account_id TEXT REFERENCES account(id),
    amount REAL NOT NULL,
    currency TEXT NOT NULL,
    occurred_at INTEGER NOT NULL,
    comment TEXT,
    attachment_photo_path TEXT,
    created_by TEXT NOT NULL REFERENCES user(id),
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    is_deleted INTEGER NOT NULL DEFAULT 0
);

-- История изменений операции (audit trail, раздел 10.4)
CREATE TABLE transaction_history (
    id TEXT PRIMARY KEY,
    transaction_id TEXT NOT NULL REFERENCES transactions(id),
    snapshot_json TEXT NOT NULL,   -- сериализованное предыдущее состояние
    changed_by TEXT NOT NULL REFERENCES user(id),
    changed_at INTEGER NOT NULL
);

CREATE TABLE budget (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL REFERENCES family(id),
    period_type TEXT NOT NULL CHECK (period_type IN ('WEEK', 'MONTH', 'YEAR')),
    period_start INTEGER NOT NULL,
    category_id TEXT NOT NULL REFERENCES category(id),
    planned_amount REAL NOT NULL
);

CREATE TABLE goal (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL REFERENCES family(id),
    name TEXT NOT NULL,
    target_amount REAL NOT NULL,
    current_amount REAL NOT NULL DEFAULT 0,
    target_date INTEGER,
    created_at INTEGER NOT NULL
);

CREATE TABLE debt (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL REFERENCES family(id),
    counterparty_name TEXT NOT NULL,
    direction TEXT NOT NULL CHECK (direction IN ('I_OWE', 'OWED_TO_ME')),
    amount REAL NOT NULL,
    due_date INTEGER,
    status TEXT NOT NULL CHECK (status IN ('OPEN', 'CLOSED')) DEFAULT 'OPEN'
);

CREATE TABLE subscription (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL REFERENCES family(id),
    name TEXT NOT NULL,
    amount REAL NOT NULL,
    billing_period TEXT NOT NULL,
    next_charge_date INTEGER NOT NULL,
    category_id TEXT REFERENCES category(id)
);

-- Служебная таблица для offline-first синхронизации (см. раздел 22)
CREATE TABLE sync_meta (
    entity_table TEXT NOT NULL,
    entity_id TEXT NOT NULL,
    local_version INTEGER NOT NULL DEFAULT 1,
    last_synced_at INTEGER,
    is_dirty INTEGER NOT NULL DEFAULT 1,
    PRIMARY KEY (entity_table, entity_id)
);
```

**Примечания к схеме:**
- Все `id` — TEXT (UUID), генерируются на клиенте в момент создания записи. Это обязательное условие offline-first: сущность должна получать постоянный идентификатор без обращения к серверу.
- `is_deleted` вместо физического удаления для `transactions` — согласуется с требованием audit trail и упрощает синхронизацию (soft delete распространяется между устройствами так же, как обычное изменение).
- Суммы денег — `REAL`. **[Открытый вопрос]:** для финансового приложения часто рекомендуют целочисленное хранение в минимальных единицах валюты (копейки/центы) во избежание ошибок округления с плавающей точкой. Стоит решить до реализации Этапа 1.

## 22. Протокол синхронизации [РЕКОМЕНДАЦИЯ]

> ⚠️ **ЧАСТИЧНО ЗАМЕЩЁН разделом 25.6.** Модель `sync_meta` и last-write-wins из раздела 22 остаются в силе; конкретный REST-контракт и реализация на Dio (Flutter) / Ktor — в разделе 25.6.

Детализация принципа Offline First (раздел 10.1) до уровня, достаточного для реализации.

### 22.1 Модель

- Каждая изменяемая сущность имеет `sync_meta` запись с полями `local_version`, `is_dirty`, `last_synced_at`.
- Любое локальное изменение → `is_dirty = 1`, `local_version += 1`, немедленное обновление UI из локальной БД.
- Фоновый sync-worker периодически (и при восстановлении сети) отправляет все `is_dirty = 1` записи на сервер.

### 22.2 Разрешение конфликтов (закрывает открытый вопрос №4 из раздела 18)

**Рекомендуемая стратегия для MVP:** last-write-wins на уровне записи, по полю `updated_at`, **с обязательным сохранением проигравшей версии в `transaction_history`** (или аналогичную историю для других сущностей, где это применимо).

Это выбрано как компромисс между простотой реализации (важно для MVP) и надёжностью (ничего не теряется безвозвратно — проигравшая версия остаётся в истории и может быть просмотрена/восстановлена пользователем). Более сложный merge на уровне отдельных полей — кандидат на пересмотр после MVP, если last-write-wins окажется недостаточным на практике.

### 22.3 Порядок разработки

1. Локальный repository возвращает данные **только** из локальной БД (Flow/StateFlow), независимо от состояния сети.
2. Запись всегда идёт через локальную БД первой; сетевой вызов — асинхронно, после.
3. Sync-worker не должен блокировать UI ни в каком сценарии.

### 25.5 Isar-схемы v1.1 (клиент)

Клиентская модель. Isar — документная NoSQL, схема генерируется из аннотированных Dart-классов через `build_runner`. Все ID — строковые UUID, совпадают с серверными. Денежные суммы — `int` (в Dart 64-битный на мобильных платформах).

Пример каркаса (полный набор коллекций даётся при реализации Этапа 0):

```dart
// mobile/lib/data/local/entities/transaction_entity.dart
import 'package:isar/isar.dart';

part 'transaction_entity.g.dart';

@collection
class TransactionEntity {
  Id isarId = Isar.autoIncrement;

  @Index(unique: true)
  late String id;              // UUID, совпадает с сервером

  @Index()
  late String familyId;
  late String accountId;
  String? categoryId;

  @enumerated
  late TxType type;            // INCOME | EXPENSE | TRANSFER
  String? targetAccountId;

  late int amount;             // копейки
  late String currency;        // 'RUB'
  late DateTime occurredAt;
  String? comment;
  String? attachmentPhotoPath;

  late String createdBy;
  late DateTime createdAt;
  late DateTime updatedAt;
```

### 25.6 Протокол синхронизации v1.1 (REST-контракт)

Дополняет раздел 22.

**Общая идея:**
- Клиент — источник изменений; сервер — точка сведения. Оба хранят `updated_at`.
- Batch pull-push: клиент периодически (и по событию) вызывает `POST /sync/push` со всеми грязными записями, затем `GET /sync/pull?since=<last_synced_at>` для получения свежих данных.
- ID генерируется на клиенте (UUID), поэтому create и update — одна операция upsert.

**Черновой контракт эндпоинтов (детализация в ADR-0005):**

```
POST /auth/register              { email, password }              → { userId, familyId }
POST /auth/login                 { email, password }              → { accessToken, refreshToken }
POST /auth/refresh               { refreshToken }                 → { accessToken, refreshToken }
POST /auth/logout-all            (JWT)                            → 204

GET  /sync/pull?since=<ISO>      (JWT)                            → { entities: {...}, serverTime }
POST /sync/push                  (JWT) { entities: {...} }        → { conflicts: [...], accepted: [...] }

POST /family/invite              (JWT) { email }                  → { inviteToken }
POST /family/accept              (JWT) { inviteToken }            → 204
```

**Конфликты:** сервер применяет last-write-wins по `updated_at`. Если серверная версия новее клиентской — клиент получает её в `conflicts` и обязан сохранить проигравшую локальную версию в `transaction_history`, затем принять серверную.

**Аутентификация:** JWT (access-token в заголовке `Authorization: Bearer`, refresh-token — через `POST /auth/refresh`). Инвалидация — через таблицу `refresh_token` (см. 25.4).
